# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

"En Navalcarnero" — a Spanish-language civic web app for residents of Navalcarnero (Madrid): events agenda, a map/directory of local businesses and services, news, transit info, activity registrations, and push notifications. All UI copy and code comments are in Spanish.

## Commands

```bash
npm install            # install deps
npm run dev             # dev server at http://localhost:5173 (also serves /api/chat locally, see below)
npm run build            # production build (vite build)
npm run preview          # preview the production build
npm run lint              # eslint .
npm run test:e2e         # Playwright: sube public/poster.jpg a Blob de verdad (ver abajo)
npm run db:setup         # apply db/schema.sql to Neon + seed the TYL TYL test org (idempotent)
npm run fetch:comercios  # regenerate src/data/comercios.json from Google Places API (also absorbs servicios-locales.json entries Google now covers — see Data layer)
npm run fetch:eventos    # regenerate src/data/eventos-externos.json from Teatro TYL TYL API + Ayuntamiento RSS
npm run fetch:noticias   # regenerate src/data/noticias.json from Ayuntamiento press feed RSS
npm run fetch:transporte # regenerate src/data/horarios-bus.json from CRTM GTFS
npm run rellenar:imagenes # manual (never cron): backfill imagen_url for ig-* rows Blob failed to upload — see "Presupuesto de Vercel Blob"
```

`npm run lint` is configured in package.json but there is no eslint config file at the project root (only inside `node_modules`) — running it will currently fail until a flat config (`eslint.config.js`) is added.

The only tests are the Playwright end-to-end specs in `e2e/`: the event poster upload (`imagen-evento`), the org profile rules (`perfil-organizacion`), the superadmin panel (`admin-super`), the featured-request flow (`destacar-evento`) and the featured duration/expiry-warning rules (`destacados-super`). They are deliberately unmocked: they drive the real dev server, the real Neon database and the real Vercel Blob store, and they clean up the events, destacados and blobs they create. They need `ADMIN_EMAIL`, `ADMIN_PASSWORD`, `SUPER_ADMIN_EMAIL`, `SUPER_ADMIN_PASSWORD` and a Blob credential in `.env`/`.env.local`. `playwright.config.js` starts the dev server on port 5199 and runs each spec on desktop and mobile viewports.

## Architecture

### Access control

The public app has **no portal password gate** — residents access all public pages freely. Management access is separated into two tiers with their own logins (see below). Legacy: the beta `AccessScreen` and `/api/acceso.js` endpoint were removed once the app opened to the public.

### Management access — two tiers

Separate from the resident password gate: `App.jsx` skips the `AccessScreen` check for `/login`, `/registro`, `/panel` and `/admin` (see `RUTAS_GESTION`), because managers sign in with their own credentials.

- **Organizations** sign in at `/login` (`POST /api/login`: env admin first, then the `usuarios` table by password hash) and land on their panel at `/panel`. New managers self-register at `/registro` with an **invite code** the superadmin issued (`POST /api/registro`). Pages: `src/pages/{Login,Registro}.jsx`, `src/pages/panel/{AdminPanel,AdminEventoForm}.jsx`, guard `src/components/admin/RutaProtegida.jsx`.
- **Superadmin** signs in at `/admin` (`POST /api/admin/login`, env `SUPER_ADMIN_EMAIL`/`SUPER_ADMIN_PASSWORD`); the same route shows the panel once logged in (`src/pages/admin/{AdminEntrada,AdminSuperPanel}.jsx`, tabs: Organizaciones, Códigos de invitación, Reclamaciones, Destacados, Pendientes, Eventos, Comercios, Analytics — the `src/components/admin/super/Tables*.jsx` components). Superadmin endpoints live in `api/super/*` behind `requerirSuperAdminEdge`.
- **Password reset for org users**: the org edit form in `/admin` has a "Usuarios y acceso" section (`TablesOrganizaciones.jsx`) backed by `api/super/usuarios.js` — `GET ?organizacionId=` lists an org's users, `PATCH ?id=` + `{password}` re-hashes it (min 8 chars, same as `/registro`; `WHERE organizacion_id IS NOT NULL` keeps vecino/superadmin rows out of reach). No email is sent — the superadmin hands the new password to the manager. There is still no self-service "forgot password" flow for managers.
- Legacy redirects: `/admin/login`→`/login`, `/admin/registro`→`/registro`, `/admin/super`→`/admin`.
- `api/_auth.js` — issues and verifies an HS256 JWT (WebCrypto, Edge-compatible) carried in a **httpOnly** cookie, shared by both tiers; the role travels in the payload. The cookie name is **conditional**: `nombreCookieAdmin()` returns `__Host-ncv_admin` in production (forces `Secure`+`Path=/`+no `Domain`) and `ncv_admin` in dev (no HTTPS ⇒ the `__Host-` prefix would be rejected). Management cookie is `SameSite=Strict` (single-origin panel), the portal cookie `SameSite=Lax`; `Secure` only in production; 8 h lifetime for management, 30 days for the portal. **Emitters and readers must always go through `nombreCookieAdmin()`/`nombreCookiePortal()`** or they desync. Guards: `requerirSesion(req, res)` (Node handlers), `requerirSesionEdge(req)` and `requerirSuperAdminEdge(req)` (Edge handlers — they return a `Response` on failure, so callers do `if (x instanceof Response) return x`).
- Almost every endpoint is an **Edge Function** (`export const config = { runtime: 'edge' }`, Web `Request`→`Response`), using the helpers in `api/_http.js` (`json`, `leerJson`, `queryDe`). Only `api/chat.js`, `api/sync-events.js` and `api/admin/imagen.js` stay on Node (`@vercel/blob`/undici, the Anthropic SDK and `web-push` need it; `api/_push-send.js` is a Node-only module imported by `sync-events.js` — never import it from an Edge handler). `api/_organizacion.js` — shared `organizacionDeSesion(sql, slug)` used by the org-scoped `api/admin/*` handlers. Session endpoints: `GET /api/admin/sesion` (who am I), `POST /api/admin/logout`. The org slug comes from the *signed* JWT, never from the request, so nobody can read or write another org's data by changing a parameter.
- Required env vars: `ADMIN_EMAIL`, `ADMIN_PASSWORD`, `SUPER_ADMIN_EMAIL`, `SUPER_ADMIN_PASSWORD`, `ADMIN_JWT_SECRET` (≥32 chars; rotating it invalidates every open session), `CRON_SECRET` (cron auth — mandatory, the cron fails closed without it). For rate-limiting: `KV_REST_API_URL`+`KV_REST_API_TOKEN` **or** `UPSTASH_REDIS_REST_URL`+`UPSTASH_REDIS_REST_TOKEN` (the Upstash Vercel integration injects one set or the other; `_ratelimit.js` accepts both). For web push: `VITE_VAPID_PUBLIC_KEY` + `VAPID_PRIVATE_KEY` (generate once with `npx web-push generate-vapid-keys`; without them the digest send is skipped with a log and the cron keeps working), optional `VAPID_SUBJECT` (`mailto:`, defaults to a placeholder). Optional: `ADMIN_NOMBRE`, `ADMIN_ORG_SLUG` (default `tyl-tyl`), `BLOB_READ_WRITE_TOKEN`. None carry the `VITE_` prefix — they must never reach the browser bundle — with **one deliberate exception**: `VITE_VAPID_PUBLIC_KEY` is public by design (the browser needs it to subscribe; the server reads the same name from `process.env`). New env vars read by dev API handlers must also be added to `VARIABLES_API` in `vite.config.js`.
- Frontend auth: `src/lib/adminAuth.jsx` — a single context for both tiers (the cookie is unreadable from JS, so it asks `/api/admin/sesion` on boot); the role is distinguished via `usuario.rol`.

### Endurecimiento de seguridad

Auditado en `SEGURIDAD.md`, implementado y desplegado (julio 2026). El detalle "en simple" está en `FLUJO_SEGURIDAD.md`; los pasos de provisión en `PUESTA_EN_MARCHA.md`.

- **Hash de contraseñas — PBKDF2** (`api/_auth.js`): `hashPassword` genera `pbkdf2$<iter>$<saltB64>$<hashB64>` (SHA-256, salt de 16 bytes, 310 000 iteraciones). `passwordCorrecto` detecta el formato: PBKDF2 lo re-deriva, y el hash antiguo (SHA-256 hex de 64 chars, sin salt) sigue validando por compatibilidad. `necesitaRehash()` marca los formatos viejos, y `api/login.js` **re-hashea de forma transparente** tras un login correcto (los usuarios migran solos). `igualSeguro` (exportada) compara en tiempo constante.
- **Rate-limiting** (`api/_ratelimit.js`, Upstash Redis vía REST, Edge+Node): `limitar({clave, limite, ventanaS})` con ventana fija (`SET … EX … NX` + `INCR`). **Fail-open con log** si Upstash no está configurado o falla (disponibilidad > protección). Aplicado a `login`, `admin/login`, `registro` (por IP+email), `analytics/track` (por IP, silencioso al exceder para no romper `sendBeacon`), `chat` (reemplaza el `Map` en memoria, inútil en serverless) y `acceso`. Lee `KV_REST_API_*` o `UPSTASH_REDIS_REST_*` (ver env vars arriba).
- **Defensa CSRF por Origin** (`api/_http.js`): `csrfInvalido(req)` es true si el método muta estado y hay `Origin` presente que no coincide con el host propio; **si no hay `Origin` se permite** (clientes no-navegador: cron, `curl`, los `afterAll` de los e2e). `rechazoCsrf()` (403) en handlers Edge; los Node (`chat`, `imagen`) responden 403 en línea. Aplicado a **todos** los handlers que mutan estado. La cookie httpOnly+SameSite ya mitigaba CSRF; esto es una capa extra.
- **Cabeceras de seguridad + CSP** (`vercel.json` → `headers`): HSTS, `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy`, y CSP con los orígenes reales (self, fuentes Google, Umami, tiles OSM, Vercel Blob). ⚠️ **PENDIENTE**: la CSP está en `Content-Security-Policy-Report-Only` (solo avisa, no bloquea). **Falta promoverla a `Content-Security-Policy` (activa)** — es un cambio de una palabra en `vercel.json`. `vercel.json` no interpola env, así que el origen de Umami va hardcodeado; el dev de Vite no aplica estas cabeceras (solo se ven en Vercel).
- **Auth del cron** (`api/sync-events.js`): valida `Authorization: Bearer <CRON_SECRET>` en tiempo constante y **falla cerrado** si falta `CRON_SECRET` (antes comprobaba una cabecera que Vercel no envía → quedaba abierto). Verificado en producción: 200 con la llave, 401 sin ella.
- **Validación de entradas**: `codStop` en `bus-times` (regex), `tipoEvento` en `track` (lista blanca) + truncado de textos, `referenciaId` en `super/destacados` (longitud+alfabeto). `chat.js` ya no filtra `err.message` al cliente.
- **Fuera de alcance (código), pendientes de negocio/jurídico**: plan Vercel Pro y papeleo RGPD/aviso legal (ver `SEGURIDAD.md`, sección de cumplimiento).

### Managing events

`api/admin/eventos.js` is a single endpoint keyed by method, with the event id in `?id=` rather than a dynamic route segment — that way one file serves every operation and the dev middleware in `vite.config.js` needs no special case:

| Method | Query | Does |
| --- | --- | --- |
| `GET` | — | list the org's events + `resumen` metrics |
| `GET` | `?id=` | one event, to pre-fill the edit form |
| — | — | (`GET /api/admin/organizacion` returns the org profile the form needs) |
| `POST` | — | create |
| `PUT` | `?id=` | replace every field |
| `PATCH` | `?id=` | change only `estado` |
| `DELETE` | `?id=` | delete |

- Every query filters by `organizacion_id`, so another org's event is a 404 rather than a leak — reading, editing, publishing and deleting it all fail. A malformed `id` is rejected against a UUID regex before touching the database.
- **The organisation's profile owns `categoria` and `lugar`.** `organizaciones.categoria_defecto` / `lugar_defecto` decide how every event of that org is published; the form shows them as read-only fields (fed by `GET /api/admin/organizacion`) and `POST`/`PUT` overwrite whatever the client sent with the profile values. Don't add a category picker back to the form without changing both sides. The superadmin sets both in the Organizaciones form ("Perfil de eventos" fields); until they're set, the event form shows a notice explaining the app team must complete the profile and disables saving (red validation marks on read-only fields would mislead the manager).
- `src/lib/eventoForm.js` is the single definition of a valid event. The form imports it to warn before submitting, and `POST`/`PUT` re-run the same `validarEvento()` server-side — the client is never trusted. `urlValida()` only accepts `http(s):`, which is what keeps `javascript:` out of the ticket link.
- **Ciclos (multi-day events)**: the form has a "ciclo" checkbox that reveals a `fechaFin` field (optional in `eventoForm.js`: must be `> fecha` and the span ≤ `MAX_DIAS_CICLO` = 31). A cycle is materialized as **one independent `eventos_usuario` row per day** (`fechasDelCiclo()` expands the range; sequential INSERTs — the Neon HTTP driver runs one statement per request) — there is deliberately **no `fecha_fin` column**: each copy is edited/published/deleted separately from the panel, and the public agenda just sees N events. `POST` with `fechaFin` creates all copies; `PUT` with `fechaFin` keeps the edited row on the start date and creates copies for the remaining days (repeating the edit creates more copies — visible and deletable in the panel, no dedup). Both respond `{evento, creados}`. Each copy gets its own `notificado_en`, so the push digest announces every day of the cycle.
- Events are rows in `eventos_usuario`, tied to the org resolved from the JWT. `estado` is `borrador` or `publicado`. `src/pages/panel/AdminEventoForm.jsx` serves both `/panel/eventos/nuevo` and `/panel/eventos/:id/editar`; with an id it pre-fills via `GET ?id=` and saves with `PUT`. Note the id format split: the panel and `api/admin/eventos.js` use the **raw uuid**; the public `api/eventos.js` prefixes it as `bd-<uuid>` (and that public form is what `destacados.referencia_id` stores).
- The `resumen` (publicados, borradores, próximos, pasados) is computed server-side on every list. The panel refetches after each mutation instead of keeping a parallel count in the client.
- `GET /api/eventos` (public, unauthenticated) returns only `publicado` rows, shaped exactly like the JSON events so the UI can concatenate them. It returns `{eventos: []}` with HTTP 200 when Neon is down, so the static agenda never breaks. `src/lib/useEventosPublicos.js` merges all three sources (`eventos.json`, `eventos-externos.json`, Neon) and is the only way a page should read the agenda — `Inicio`, `Eventos` and `EventoDetalle` all use it. DB ids are prefixed `bd-` to avoid colliding with the JSON ids. The hook memoises the merged array so callers can use it as a `useMemo` dependency. **Dedup en el merge** (`src/lib/dedupEventos.js`, módulo limpio sin JSX/JSON): un evento de Neon con la misma fecha y título equivalente (normalizado sin acentos/puntuación; igualdad o contención ≥ 12 chars) que uno estático se **fusiona** en la tarjeta estática — la versión curada es la base y la de Neon solo rellena campos vacíos (típicamente `imagen`, el cartel real de Instagram) — así el mismo evento anunciado en el programa VIVE y en un post del Ayuntamiento no sale dos veces. El id del duplicado queda en `idsSecundarios`: `EventoDetalle` resuelve deep links por id principal o secundario, y `useDestacados` indexa ambos, de modo que avisos push y destacados que referencien el `bd-…` siguen funcionando. Trade-off aceptado: al ganar el id estático, la visita no se atribuye en "Mis analíticas" de la org (solo cuenta para eventos cuyo id principal es `bd-…`).
- `EventoDetalle` links the venue name to a Google Maps search for `"<lugar>, Navalcarnero, Madrid"` — events only store the venue name, never coordinates.
- Date columns are formatted with `to_char(..., 'YYYY-MM-DD')` in SQL. The Neon driver returns `date` as a JS `Date`, and converting it in JS drags the timezone in.
- `POST /api/admin/imagen` uploads the poster to Vercel Blob and returns its URL, which the form then submits as `imagen` and the API stores in `eventos_usuario.imagen_url`. The image travels base64-encoded inside the JSON body (not multipart) so it reuses the same body parsing as every other endpoint; Vercel caps a function body at 4.5 MB and base64 inflates by a third, hence the 3 MB limit. With no Blob credential the endpoint 503s with a clear message and the rest of the form keeps working — the image is optional. Org sessions upload to `eventos/<slug>/…`; a superadmin session (no org slug) falls back to `destacados/…`. `src/components/admin/SelectorImagen.jsx` is the reusable upload widget (props `etiqueta`/`opcional`).
- **Blob auth gotcha.** `@vercel/blob` prefers OIDC whenever it finds `VERCEL_OIDC_TOKEN` *and* `BLOB_STORE_ID`, falling back to `BLOB_READ_WRITE_TOKEN` only if neither is set. OIDC is not permitted in the `development` environment, so locally that preference makes every upload fail with `BlobOidcEnvironmentNotAllowedError`. `api/admin/imagen.js` therefore passes `token:` explicitly when `BLOB_READ_WRITE_TOKEN` exists, and lets OIDC take over on Vercel. Anything else calling `put`/`del`/`list` (including the e2e cleanup) must do the same.

#### Actividades deportivas: cada cartel necesita su propia `url`

`combinarSinDuplicados()` (`api/sync-events.js`) deduplica **por `url` antes que por título+fecha**: el primer evento con una url dada la registra y cualquier otro que repita esa url se descarta sin mirar nada más. `api/_actividades-deportes-feed.js` asignaba a los 36 carteles una misma `url_fuente` hardcodeada ⇒ **sobrevivía uno y se perdían 35**, incluidos los 28 que no emparejan con nada. Latente desde que se añadió la fuente (ago 2026); todos los cron reales emitieron exactamente 1 actividad deportiva hasta que se arregló.

La url que se usa ahora es el `href` de la galería de WordPress (página de adjunto del cartel: `…/actividades-deportivas-…/34-torneo-ajedrez-5-sept/`), único por cartel y ya extraído por el parser. **Hay tres sitios que construyen actividades** (cartel emparejado, cartel suelto y huérfana reconstruida desde "fin de plazo"): los tres deben poner url propia — un cuarto sitio que caiga a una url compartida reintroduce el fallo entero. Sin `href` se pone `''`, nunca la página común: la cadena vacía desactiva esa regla para esa fila, la página común *es* la colisión.

Efecto en el frontend: `evento.url` solo se pinta en `EventoDetalle` ("Ver en la web del ayuntamiento"); las tarjetas usan `entradas?.url`, que es otro campo.

#### Los carteles emparejados viven en el JSON aunque no se pinten

La fusión cartel→evento del programa es **client-side**: `enriquecerPorCartel()` (`src/lib/dedupEventos.js`, llamada desde `useEventosPublicos`) filtra los carteles con `enriqueceEvento` para que nunca salgan como tarjeta y le inyecta **solo la imagen** al evento que citan — el programa manda en titulo/fecha/hora/lugar/descripcion/url aunque los tenga vacíos (un cartel es un JPG con el título rotulado; sus campos derivados del nombre del fichero son menos fiables). Por eso `eventos-externos.json` **debe contener** esos carteles: no son basura que sobre, son el soporte de la imagen y del marcador. Un `enriqueceEvento` que no resuelva a ningún evento presente hace que el cartel se muestre como evento propio (fail-soft) en vez de desaparecer.

#### Carteles deportivos nuevos sin emparejar → revisión humana (no publicación directa)

Desde `feat/deportes-nuevos-a-revision`: un cartel del feed de deportes que **NO empareja** con el programa de fiestas y cuyo id **no está grandfathered** ya no entra en `eventos-externos.json` — se inserta como **borrador en la tabla `actividades`** de Neon (`categoria='deporte'`, `fecha_evento`/`fecha_limite` según el cartel, `lugar='Navalcarnero'`, `origen_externo_id` = el id estable de siempre) y pasa por la bandeja **Pendientes** de `/admin`, igual que el contenido de Instagram. Los que **SÍ emparejan** (`enriqueceEvento` resuelve) siguen exactamente igual: al JSON, solo aportan imagen.

- **Reparto de responsabilidades — el insert vive en el cron, NUNCA en el feed**: `separarDeportesParaRevision()` (pura, clasifica) y `upsertDeportesEnRevision()` (escribe en Neon) viven en `api/_deportes-revision.js`; el feed solo llama a la primera y `api/sync-events.js` a la segunda, en un try propio (un fallo de Neon no rompe la sincronización; el cartel se re-ve en el siguiente run). Motivo: `obtenerActividadesDeportivas()` la importan también los scripts de diagnóstico (`scripts/contar-duplicados*`), y un diagnóstico no debe crear borradores reales. El upsert es por `origen_externo_id` y **no toca `estado` ni `publicado_en`** (mismo patrón que el webhook de noticias: un archivado no resucita, un publicado no vuelve a borrador). Devuelve además `filasCreadas` (`{titulo, fecha}` de las realmente insertadas, no las actualizadas): con ellas `sync-events.js` avisa al superadmin por email (`enviarEmailPendientes`, try propio, fail-soft) — un cartel re-visto en runs siguientes no re-avisa.
- **No retroactivo — lista de exclusión explícita de 36 ids** (`api/_datos/deportes-grandfathered.js`): los 36 `origen_externo_id` presentes en el JSON committeado en la fecha de corte (2026-08-25) — los 28 sin emparejar **y también los 8 emparejados**. Grandfathered es **una propiedad del id, no del estado de matching**: un grandfathered que deje de emparejar mañana NO se mueve a Neon (caería al fail-soft de siempre: tarjeta propia publicada). Con solo los 28, un emparejado que dejara de emparejar se movería retroactivamente — justo lo que la no-retroactividad prohíbe. La lista es una foto histórica: **no añadir ids nuevos**.
- **Decisión por ejecución para los post-rama**: un cartel nuevo que empareje hoy va al JSON; si en un run futuro deja de emparejar, pasa a revisión en ese run (más seguro que el fail-soft de auto-publicarlo). Se descartó el grandfathering dinámico ("todo lo que alguna vez estuvo en el JSON") porque exige leer el JSON anterior, que en local sin `GITHUB_TOKEN` se lee vacío — habría clasificado todo como nuevo e insertado borradores reales en cada verificación local.
- **Limitación conocida (aceptada, no resolver aquí)**: los ids sin componente de fecha (`deportes-plazo-*`, fallbacks sin número como `deportes-waterpolo`) pueden regenerarse idénticos en una temporada futura y se darían por grandfathered, saltándose la revisión.
- **Cambios de semántica aceptados**: (1) un cartel aprobado desde Pendientes entra en la agenda **sin push** (las actividades no tienen digest — coherente con toda la tubería de actividades, pero es una pérdida respecto al camino JSON, que pasaba por `push_avisos`); (2) las **huérfanas de plazo** futuras se modelan bien (`fecha_evento NULL` + `fecha_limite`) en vez de con la fecha del plazo como si fuera la del acto, que es lo que hace el camino JSON; (3) un cartel sin fecha ninguna, aunque se publique, sigue invisible en la agenda (el mapeo de `useEventosPublicos` exige `fecha_evento || fecha_limite`) — esta rama NO resuelve la visibilidad de los sin-fecha, que sigue pendiente como decisión de producto.
- **Observabilidad**: la fila `deportes` de `ingesta_log` lleva dos motivos nuevos — `'nuevo sin emparejar → revisión'` y `'grandfathered (publicado directo)'` — que son **contadores informativos de tubería, NO descartes** (`descartados` se pasa explícito, no como suma de motivos). `nuevos` sigue contando el total emitido (JSON + revisión), así que la identidad `candidatos = nuevos + descartados` no cambia. El cron añade `deportesARevision`/`deportesRevisionCreadas`/`deportesRevisionActualizadas` a `estadisticas`.
- **Verificación**: hoy ningún cartel real ejercita el camino nuevo (los 36 están grandfathered), así que `e2e/deportes-revision.spec.js` lo cubre con un **cartel sintético** (id fuera de la lista, sin match) contra el Neon real: clasificación, borrador → Pendientes → descartar/publicar → re-run sin duplicado ni resurrección → tarjeta en `/eventos` → limpieza. La regresión de los 36 se verificó con el feed en vivo: salida del feed idéntica byte a byte antes/después del cambio (36 al JSON, 8 emparejados, 0 a revisión) y 0 filas `deportes-%` en `actividades`.

#### Matcher canónico (`src/lib/dedupEventos.js` — 1a construido; adopción completa: 1b, 1c y 1d hechas)

Las tres lógicas de "¿son el mismo evento?" que estaban reimplementadas por separado viven ahora consolidadas en `src/lib/dedupEventos.js` como **primitivas** (`claveTitulo`, `palabrasSignificativas`, `claveNormSlug`, `normalizarPalabraDeportiva`/`palabrasClaveDeportivas`/`solapamientoDeportivo`) y **tres matchers con nombre** — deliberadamente NO una función universal, porque las tres situaciones son distintas:

| Matcher | Sitio que debe usarlo | Criterio |
| --- | --- | --- |
| `titulosEquivalentes` | Agenda pública (`combinarEventos`) y webhooks IG — **ya lo usan** (era el canónico; webhooks auditados y confirmados, ver Estado de adopción) | Títulos limpios: igualdad sin palabras vacías o contención ≥12 chars |
| `emparejarCartelConPrograma` | `api/_actividades-deportes-feed.js` — **migrado (rama 1d, 2026-08-24)**: el feed importa el matcher y `claveNormSlug` del módulo; sus copias locales (`encontrarEventoEnPrograma`, `contarPalabrasCoincidentes`, `normalizarPalabra`, `normalizarParaMatching`, `claveNormPrograma`) se eliminaron. #### Matcher aproximado de la agenda — SOLO eventos del Ayuntamiento (`titulosAproximados`)

El mismo acto llega a la agenda con títulos redactados distinto en el programa de fiestas y en el post de Instagram del Ayuntamiento ("TROFEO FIESTAS PATRONALES CD FUTSI NAVALCARNERO." vs "Trofeo fiestas patronales futbol sala") y `titulosEquivalentes` no los reconoce ⇒ tarjeta doble. Para cualquier otra org, club o actividad el comportamiento no cambia: sin equivalencia canónica, dos tarjetas como siempre.

- **Campo que identifica la organización**: `evento.organizacionSlug`, añadido al `GET /api/eventos` público (`o.slug` del JOIN, mismo nombre que usa el cron). Se eligió el slug y no `fuente` (el nombre) porque el slug es estable aunque se renombre la org. Las actividades mapeadas a eventos no llevan slug ⇒ nunca pasan la puerta.
- **Criterio** (los tres a la vez): mayoría **estricta** de las palabras significativas del título más corto presente en el más largo — proporcional a propósito, no un nº fijo como el matcher deportivo —, mínimo 2 compartidas en absoluto, ignorando siglas de entidad de club (`cd`, `club`: "CD FUTSI" y "Futsi Atlético" son el mismo club), y **veto de compuesto divergente**: una palabra compartida seguida de `de/del/sobre` + una palabra que el otro título no tiene ("tenis **de mesa**") nombra otra disciplina y anula la fusión aunque el solapamiento sea del 100 %. El tab Eventos del superadmin (`TablesEventos.jsx`) muestra junto a la categoría una etiqueta discreta con la **vía por la que cada evento entró en la agenda** — solo ahí, la agenda pública no la pinta en ningún sitio. | --- | --- |
| `fiestas-*` | Programa oficial |
| `deportes-*` | Galería de Deportes |

#### Verificar un cambio en el cron: ejecución real, no simulación

Dos veces seguidas se dio por bueno un cambio del cron mirando el fichero committeado o un script local que reproducía "el trozo interesante" del pipeline. Ambas fallaron: el JSON committeado puede venir de una ejecución anterior, y un script que salta la función que rompe (aquí `combinarSinDuplicados`) no verifica nada. Un JSON generado a mano llegó a producción con 158 eventos **sin `id`** porque el script usaba el módulo crudo en vez de `eventosFiestas()`.

La verificación válida es: desplegar, esperar a que Vercel esté `Ready`, `POST https://ennavalcarnero.es/api/sync-events` con `Authorization: Bearer $CRON_SECRET`, y contar sobre el **commit que genera el propio cron**:

```bash
git show <commit>:src/data/eventos-externos.json | jq '[.[]|select(.origen=="deportes")]|length'          # 36
git show <commit>:src/data/eventos-externos.json | jq '[.[]|select(.origen=="deportes")|.url]|unique|length' # 36 — si baja, hay urls compartidas
git show <commit>:src/data/eventos-externos.json | jq '[.[]|select(.enriqueceEvento!=null)]|length'        # 8
```

Ojo con CRLF: `git show` de este repo devuelve `\r\n`, así que cualquier `comm`/`diff` sobre esa salida necesita `tr -d '\r'` o dará el 100 % de las líneas como distintas.

Y la regla general de la que esto es un caso: cuando un pipeline construye objetos **campo a campo** en vez de con spread, cualquier campo nuevo añadido aguas arriba se pierde en silencio (no hay error de compilación). Al añadir uno, localiza **todos** los sitios que reconstruyen el objeto.

#### Guardas de fecha en los comparadores (defensivo; NO decide visibilidad)

Los `.sort()` que comparaban `fecha` sin guarda llevan ahora `(x.fecha || '').localeCompare(y.fecha || '')` (el mismo patrón que ya usaba `sync-events.js`) para que un evento con `fecha` null/ausente no pueda tirar la página con un TypeError. **Cambio puramente defensivo, verificado sin cambio de comportamiento** contra los datos reales (305 eventos, incluidos los 21 carteles deportivos con `fecha: null`): mismo orden con comparador viejo y nuevo en todos los sitios, y capturas de Playwright de `/eventos`, `/noticias` y una ficha de comercio idénticas línea a línea antes/después.

- `src/lib/eventos.js` — `proximosEventos()`, `eventosPasados()` y `agruparEventosPorDia()`: guarda en el sort. Los `.filter()` previos (`aFecha(e.fecha) >= hoy`) **no se tocaron**: son los que deciden qué se ve hoy (excluyen los `fecha: null` vía Invalid Date), y esa decisión no es de esta guarda. `agruparEventosPorDia` era el único que crashearía de verdad si algún día recibiera datos sin filtrar.
- `src/pages/PerfilComercio.jsx` (`proximasFunciones`) — **mecanismo distinto, documentado en el propio código**: su filtro compara `e.fecha >= hoy` como STRING (sin pasar por `aFecha`), así que con `fecha` null la coerción relacional da `0 >= NaN` = false y el evento queda fuera implícitamente. La guarda va en el sort que sigue al filtro.
- `api/_noticias-feed.js` — **sin guarda a propósito** (comentado en el código): el paso 1 de `obtenerNoticiasPrensa()` descarta cualquier item RSS sin fecha parseable (`if (!titulo || !fecha) continue`; `fechaISO()` devuelve `''` si el pubDate no parsea), así que su sort nunca ve `fecha` ausente. Solo procesa el RSS de prensa; las noticias de Instagram se ordenan aparte en `useNoticiasPublicas`, cuyo sort ya llevaba guarda.
- Hallazgos del grep final de `localeCompare` sobre fechas: `scripts/fetch-eventos.mjs` tenía el mismo patrón sin guarda y se le aplicó también; `src/lib/useActividades.js` ya estaba protegido explícitamente (checks null-last antes del `localeCompare`, y un filter `fecha_limite &&` en el otro sort); `TablesEventos.jsx`, `useNoticiasPublicas.js` y `sync-events.js` ya llevaban guarda.

⚠️ **Esta rama NO resuelve dónde/si se muestran los 21 eventos deportivos con `fecha: null`** — siguen excluidos de la agenda por los filtros previos, igual que antes. Esa visibilidad es una decisión de producto aparte, pendiente de verse montada antes de aprobarse.

### Destacados (paid featured items)

Featuring an event or a business is a **paid product** (payment agreed outside the app for now; Stripe is a designed-for future phase). One source of truth: the `destacados` table (`tipo` evento|comercio, `referencia_id` as opaque public-format text — `ev-…`/`aytocult-…`/`bd-<uuid>` for events, `gpl_…`/`local/…` for comercios —, `organizacion_id` = who contracted it, `orden`, `imagen_url`, `fecha_inicio`/`fecha_fin`, `estado` pendiente|activo|cancelado). Validity is computed **at read time** (no cron): expired rows just stop appearing. `UNIQUE (tipo, referencia_id)` — one row per item, re-featuring reuses it, so there is deliberately **no campaign history**.

- **Public read path**: `GET /api/destacados` (Edge, no auth, CDN cache 60 s, `{destacados: []}` with HTTP 200 if Neon is down) returns the raw in-vigor list; resolution to full objects happens **client-side** in `src/lib/useDestacados.js` (the browser already has all comercios and static events imported) using the adapters in `src/lib/destacados.js` (`eventoATarjeta`/`comercioATarjeta`, plus the `COMERCIOS_POR_ID` map). Dead references and past events are silently filtered.
- **Rotation (looping window)**: `useDestacados` returns **all** in-vigor items in the superadmin's `orden`; the slot allocation lives in `CarruselDestacados`. With more items than `visibles` (defaults to `columnas`; Inicio 4, Eventos 3, Comercios 6), on **md+** it switches to a sliding track (overflow-hidden + flex with N+1 cards, slot width via the `--nv-hueco` CSS var consumed by `.nv-pista` in `index.css`, which must stay in sync with the track's gap): every 5 s the track animates `translateX` exactly one card left (distance measured live: card width + gap) and on `transitionend` commits `paso` and resets the transform without transition — a seamless infinite loop, so every contracted item slides through the screen for the same visitor. On **mobile** there is no track: the native scroll-snap carousel renders **all** items so swiping remains the way to browse them (the track's overflow-hidden would kill manual scroll); the advance interval skips ticks while the track is hidden (width 0). Random start offset per mount (short visits don't always see the same ones), pauses on hover and for 12 s after a touch (cards must not swap under the cursor/finger — `mouseenter`/`mouseleave` on purpose, touch `pointerenter` has no reliable leave), and doesn't auto-advance under `prefers-reduced-motion`. With ≤ `visibles` items the list is static. Rotation lives client-side on purpose: dead-reference filtering only exists in the browser, one cached response serves all three surfaces, and the 60 s CDN cache stays untouched.
- **Duration**: the superadmin form sets duration via presets (7/15/30 days, `PRESETS_DURACION` in `TablesDestacados.jsx`) that compute `fecha_fin = fecha_inicio + N − 1` (inclusive — `fecha_fin >= CURRENT_DATE` keeps the item visible on its last day). `validar()` in `api/super/destacados.js` requires `fechaFin` on POST/PUT, and PATCH refuses to set `activo` on a row without `fecha_fin` (400) — the UI opens the edit form instead when approving a dateless `pendiente`, so approval is: click badge → set duration → save → click badge again. The column stays NULLABLE deliberately: pre-proposal pending rows and legacy "sin fin" rows exist, and they stay valid until first edited (new org requests always carry a proposed vigencia). **Accepted trade-off**: pre-existing `activo` rows without `fecha_fin` read as never-expiring in the public GET and never trigger the expiry warning; there is no migration or backfill — the first edit (duration selector starts empty and blocks submit) or re-activation forces a duration, and cleaning them up earlier is a manual superadmin task. Editing infers the preset from the current dates; non-standard durations get a "Personalizada (N días)" option so re-saving doesn't alter them.
- **Expiry warnings**: computed client-side (both admin GETs already return `fechaFin` + `vigente`; no endpoint changes). `src/lib/fechas.js` holds the shared date primitives (`hoyISO`, `sumarDias`, `diasHasta`, `UMBRAL_AVISO_CADUCIDAD = 5`) — it replaced the `hoyISO` that was duplicated in `AdminPanel.jsx`. `src/lib/destacados.js` exposes `diasParaCaducar()` (null unless activo + vigente + ≤ 5 days left), `textoCaducidad()` and `campanaFinalizada()` (activo whose term ended — not the same as `!vigente`, which also covers not-yet-started). Three surfaces show "caduca en N días": the super table (next to the existing "fuera de plazo" badge — mutually exclusive by construction), `FilaEvento` and `DestacaNegocio` in `/panel` (amber `tertiary-container` variant of the "Destacado" badge). When the campaign ended, the panel shows a neutral "Destacado finalizado" instead of the green badge. Renewal stays a human channel (WhatsApp/email): the warning is the hook, there is no in-app renewal request.
- **Click tracking**: `reportarClicDestacado()` in `useAnalytics.js` logs `clic_destacado` rows (via `sendBeacon`, survives Link navigation) with the surface in `seccion` (`inicio|eventos|comercios`), reusing `evento_id`/`organizacion_id` for `bd-` events and `comercio_buscado` for comercios — static events only log surface. The `seccion` prop on `CarruselDestacados` enables it; no schema change. No report UI yet — the signal accumulates for future renewal arguments.
- **Future work (deliberate, don't build piecemeal)**: a "solicitar renovación" button in `/panel` was considered and rejected while approval is 100 % manual — it only pays off together with automated billing, so build it with the Stripe phase. Likewise, the no-campaign-history decision (`UNIQUE (tipo, referencia_id)`, rows are reused) weighs more now that fixed durations make renewals recurring ("how many times did this client renew" becomes a retention metric) — acknowledged, still not reopened.
- **UI**: `src/components/destacados/TarjetaDestacado.jsx` (full-bleed photo, dark bottom gradient, category pill; comercios without a photo fall back to their category color + big icon) and `CarruselDestacados.jsx` (scroll-snap carousel on mobile, grid on desktop, `soloCarrusel` for narrow columns). Three surfaces: Inicio (mixed teaser, 4), Eventos (its own "Destacados" section above "Próximos eventos", 3 — with none in vigor the page falls back to the classic first-upcoming hero; with a category filter active the carousel hides), Comercios (business strip above the list, 6, hidden while filtering/searching; clicking selects the ficha in place).
- **Self-service from `/panel`**: a "Destacar" button on each published future event (opens `DialogoSolicitudDestacado`) and a "Destaca tu negocio" card (photo required, uploaded to Blob) if the org has a linked business. Both propose **start date + duration** (shared `CamposPropuestaDestacado` fieldset, presets with their tarifa shown). Requests go through `api/admin/destacados.js` (org-scoped): POST forces `estado='pendiente'`, derives the `bd-<uuid>` reference server-side after ownership/publicado/future checks, validates the proposal (start not in the past, duration ∈ `PRESETS_DURACION`) and computes `fecha_fin` server-side — **`orden` stays superadmin-only**; DELETE withdraws an own pending request. A rejected request (`cancelado`) shows **no badge** to the org — the button simply reappears, and re-requesting resurrects the same row with the new proposal. Each org destacado's badge in `/panel` opens `DetalleDestacado` (estado, vigencia, duración, tarifa, imagen).
- **Tarifas**: `src/lib/tarifasDestacados.js` — `PRESETS_DURACION` + `TARIFAS_DESTACADO` (per-duration price, **placeholder amounts pending business confirmation**). Deliberately a "clean" module (no JSX/JSON) because Edge handlers import it too; don't add browser-dependent code there. There is **no price column** — price derives from duration.
- **Backoffice**: the Destacados tab in `/admin` (`TablesDestacados.jsx` + `api/super/destacados.js`) lists everything with contratante, vigencia and estado; pendiente rows show their dates tagged "propuesta", and clicking the `pendiente` badge approves/activates with them (via the edit form first if the row has no duration — see **Duration** below); "Rechazar" cancels without passing through activo; the edit form sets orden/inicio+duración/imagen. The tab button in `AdminSuperPanel.jsx` shows a **pending-requests counter** (refetched on mount and on tab change).
- **Org↔business link**: `organizaciones.comercio_id` (text, partial unique index — one business belongs to at most one org) is set by the superadmin in the Organizaciones form via a directory search picker. Unlinking does **not** clean up that business's destacados (managed manually). **Form gotcha**: the org form must round-trip every column the PUT replaces — it carries `categoriaDefecto`/`lugarDefecto` invisibly precisely because a save without them wipes the org's event profile.

#### Tarjeta de evento sin imagen (plantilla editorial)

La tarjeta del muro de la cartelera (`TarjetaEvento.jsx`, el único componente de tarjeta vivo — `EventoFila.jsx`/`EventoFilaNueva.jsx` no los importa nadie) tiene dos variantes: con cartel real (`imagen_url` ⇒ foto a sangre, **sin tocar**) y sin imagen (degradado de categoría + trama). La variante sin imagen lleva una plantilla editorial, toda condicionada a `!posterUrl`:

- **Fecha editorial** arriba a la derecha: día en `font-serif-dm` grande + mes en 3 letras mayúsculas en `font-mono-ibm` atenuado (`mesDe(fecha).slice(0, 3)`). Con sello "Destacado" se baja (`top-11`) para no pisarlo. Guarda de `evento.fecha` (los carteles con `fecha: null` no la pintan).
- **Organizador** bajo el lugar, mono pequeño atenuado, `Organiza · {evento.fuente}` — solo si el evento trae `fuente` (mismo campo que el "Organiza" de `EventoDetalle`).
- **Remate de categoría**: icono Tabler de 60px, rotado 8°, opacidad 0.10, pegado a la etiqueta de categoría (anclado a la fila del eyebrow, primer hijo del bloque de contenido para quedar debajo del texto). Es una **firma editorial junto a la etiqueta, NO un watermark de fondo** — no moverlo a la esquina ni agrandarlo sin releer el párrafo siguiente.
- **Por qué se descartaron las otras dos variantes del icono** (comparadas con capturas reales de un día con 6 tarjetas de deporte apiladas, 2026-08-27): la versión "esquina" (~150px, opacidad 0.10, recortado por la esquina superior derecha) estampaba el mismo icono en la misma esquina de cada tarjeta — con varias tarjetas de la misma categoría apiladas en un día leía como patrón de papel de regalo, y además competía con la fecha editorial, que vive en esa misma esquina. Bajar la opacidad a 0.05 (variante A) resolvía la repetición **por sustracción**: el icono quedaba tan fantasmal que ya no aportaba nada, y cuando llegaba a percibirse seguía siendo el mismo motivo en la misma esquina. El remate pequeño junto a la etiqueta mantiene el icono legible y con función (identidad de categoría de un vistazo), atenúa la repetición al no dominar la superficie, y deja la esquina para la fecha.

**`iconoDeCategoria(categoria, subcategoria)`** (`src/lib/eventos.js`, junto a `CATEGORIAS_EVENTO`) es la función pura que decide el icono y devuelve un **slug `ti-*`**, no un componente — ese módulo lo importan también handlers de API y debe seguir "limpio" (sin JSX). El mapeo slug → componente (`TABLER_POR_SLUG` + `IconoCategoriaTabler`) vive en `src/components/eventos/iconosEvento.jsx`. Mapa: `fiestas+religiosa → ti-building-church` (Tabler no tiene `church` a secas), `fiestas → ti-confetti`, `cultura+teatro → ti-masks-theater`, `cultura → ti-books`, `gastronomia → ti-glass-champagne`, `mercado → ti-shopping-bag`, `deporte → ti-run`, `infantil → ti-mood-kid`, `talleres → ti-tool`, `mayores → ti-armchair`, `ayudas → ti-heart-handshake`, `empleo → ti-briefcase`, `educacion → ti-school`, `general → ti-calendar` (también el fallback de categoría desconocida). Si algún día hace falta más finura (ajedrez, natación, teatro específico...), la tercera capa mirando el título del evento se añade **dentro de esta función** — no antes: hoy los datos no lo justifican (la nota vive también como comentario en la función).

Verificado con Playwright sobre datos reales (2026-08-27): capturas de 6 categorías sin imagen (deporte, cultura, fiestas religiosa con la iglesia, mercados, infantil, gastronomía); 9 tarjetas con imagen —incluidas las fusionadas (voleibol, master class)— **idénticas byte a byte (SHA-256) antes/después** del cambio; y aserción programática sobre las 175 tarjetas de la agenda: el bloque de fecha editorial aparece en las 129 sin imagen y en ninguna de las 46 con imagen. Ojo al leer capturas a ojo: varios carteles reales llevan su fecha rotulada dentro del propio JPG ("VIERNES, 28 DE AGOSTO" en el del baloncesto 3x3) — no confundirla con la capa editorial; ante la duda, comprobar el DOM.

#### Compartir contenido: BotonCompartir parametrizado

`src/components/BotonCompartir.jsx` es un componente reutilizable para compartir contenido en móvil (Share API nativa) y escritorio (popover con opciones). Acepte props opcionales para customizar el contenido compartido:

```jsx
<BotonCompartir
  titulo="En Navalcarnero"         // Título del share nativo (default: 'En Navalcarnero')
  url={window.location.origin}     // URL a copiar/compartir (default: origin)
  textoCompartir={null}            // Texto enriquecido para share/email (default: "Descubre la app...")
  conEmail={false}                 // Si true, añade opción "Enviar por correo" en escritorio
/>
```

**Comportamiento:**
- **Móvil**: `navigator.share()` nativo con el payload customizado.
- **Escritorio**: popover con botones (Copiar enlace, WhatsApp Web, y opcionalmente Email).
- **Guardas defensivas**: todos los textos se codifican con `encodeURIComponent` para manejar acentos, símbolos y saltos de línea sin romper URLs ni enlaces mailto.

**Decisión de UX para `conEmail`**: en modo "compartir app" (Inicio) no tiene sentido ofrecer email (es solo un enlace); en modo "compartir evento" (EventoDetalle) es natural. El flag permite reutilizar el componente sin exponer la opción donde no tiene valor.

**Uso en EventoDetalle:** El texto compartido es enriquecido con fecha y lugar del evento, formateado en múltiples líneas:
```
Título del evento
Sábado, 1 de septiembre · Lugar del evento
https://…
```
Guarda contra `evento.fecha === null` (carteles deportivos sin fecha): omite la línea de fecha pero mantiene lugar si existe, o solo título + URL si faltan ambos.

### Database (Neon Postgres)

The Neon project `navalcarnero-db` is provisioned through the Vercel Marketplace integration, so all `DATABASE_URL`/`POSTGRES_*` variables are injected into the Vercel environment automatically. For local work, run `npx vercel env pull .env.local` — `vite.config.js` forwards `DATABASE_URL` to the dev API handlers, and `scripts/db-setup.mjs` reads `.env.local` (falling back to `.env`).

- `db/schema.sql` — canonical schema. Core tables: `organizaciones` (cultural orgs and business-owner accounts; `comercio_id` links one to its directory entry), `codigos_invitacion` (invite codes the superadmin issues so an org's managers can sign up), `usuarios` (`admin`/`editor` belong to an org, `vecino`/`superadmin` don't), `eventos_usuario` (events created in-app, in `borrador`/`publicado`/`archivado`), `analytics` (anonymous usage events) and `destacados` (paid featured items — see **Destacados** above); later features added `push_suscripciones`/`push_avisos` (push), `noticias_instagram`/`actividades` (Instagram sync), `eventos_ocultos`, `solicitudes_reclamacion`/`comercios_perfil` (reclamaciones) and `ingesta_log` (observabilidad de la ingesta) — each documented in its feature section. Statements are split on a trailing `;` by the setup script, so don't add functions or dollar-quoted blocks. `CREATE TABLE IF NOT EXISTS` won't add columns to a table that already exists, so new columns also need an `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` at the end of the file.
- `scripts/db-setup.mjs` (`npm run db:setup`) — applies the schema and seeds the test org **Teatro TYL TYL** (`slug: tyl-tyl`) with invite code **`TYLTYL-2026`** (grants `admin`, 5 uses). Idempotent via `ON CONFLICT`.
- `api/_db.js` — `obtenerSql()` returns a memoized `@neondatabase/serverless` HTTP client (tagged template). Underscore prefix keeps Vercel from deploying it as an endpoint.
- `api/health.js` — `GET /api/health` verifies the connection and that the tables in `TABLAS` (`api/_db.js`) exist; returns 503 if either fails. A new table must be added to `TABLAS` or health won't check it. Live at https://naval-app-one.vercel.app/api/health.

The Neon HTTP driver runs one statement per request; multi-statement SQL will not work.

### Presupuesto de Vercel Blob

El plan gratuito de Vercel Blob incluye **2 000 "Advanced Requests" al mes** (`put`, `list`, `del`, `head` — las lecturas por URL pública, es decir servir una imagen ya subida, **no** cuentan). Es una restricción de diseño transversal: **cualquier código nuevo que llame a `put`/`list`/`del`/`head` de `@vercel/blob` debe contar cuántas de esas llamadas hace por ejecución** y, si el volumen es alto (un cron, un webhook, un bucle sobre muchos items), comprobar antes contra Neon si la operación es evitable — Neon no tiene ese coste. **`head()` no sirve para comprobar si un blob ya existe**: también consume un Advanced Request, así que "preguntar a Blob" para ahorrarse un `put()` no ahorra nada. La comprobación de existencia va siempre contra la base de datos (columna `imagen_url`/`imagenes_url`, ver más abajo), nunca contra Blob.

**El store es compartido entre todos los flujos que suben imágenes**, no solo Instagram — agotar la cuota deja sin subir fotos a comercios y eventos por igual:

| Prefijo del blob | Quién sube | Dónde |
| --- | --- | --- |
| `comercios/<id>/…` | Ficha enriquecida de un comercio (foto principal + hasta 5 fotos adicionales) | `api/admin/imagen-comercio.js` |
| `eventos/<slug>/…` | Cartel de un evento publicado desde `/panel` | `api/admin/imagen.js` |
| `destacados/…` | Imagen de una solicitud de destacado (comercio) sin org enlazada | `api/admin/imagen.js` |
| `instagram/…` | Cartel de un evento sincronizado desde Instagram | `api/sync-instagram.js` |
| `instagram-noticias/…` | Foto(s) de una noticia/alerta sincronizada desde Instagram (galería completa) | `api/sync-instagram-noticias.js` |
| `instagram-actividades/…` | Foto de una actividad (fila única, o una por cartel de un carrusel) | `api/sync-instagram-noticias.js` |

Los tres últimos son, con diferencia, los que más `put()` pueden llegar a generar: un solo run de Apify trae ~50 posts, muchos ya procesados en runs anteriores. **`normalizarPost`/`subirImagen` (`api/_instagram.js`) y los dos webhooks consultan Neon antes de subir nada** — si el `origen_externo_id` ya tiene `imagen_url` (o, en noticias, `imagenes_url`) guardada, se reutiliza esa URL sin llamar a `subirImagen`; solo se sube si la fila es nueva o si una subida anterior dejó la imagen a `NULL` (reintento). Un fallo de Blob (cuota agotada, store pausado, red) nunca aborta el upsert: `subirImagen` atrapa cualquier error y devuelve `null`, y el evento/noticia/actividad se guarda igual con `imagen_url` a `NULL` — así el pipeline puede seguir corriendo (y creando contenido) durante una pausa del store, sin perder nada que no sea la foto. `scripts/rellenar-imagenes.mjs` (`npm run rellenar:imagenes`, manual, no en el cron) recupera después esas imágenes pendientes.

**Emparejamiento de fotos de carrusel: por id estable, no por título.** Cuando una hija de un carrusel (`actividades`, ver más abajo) ya tiene imagen y se reutiliza, el emparejamiento entre "esta foto de este run" y "esta fila ya existente" se hace primero por `imagen_origen_id` (el media id/shortcode que Instagram asigna a cada foto de un Sidecar — `id` en `carruselDe()` de `api/_instagram.js`, columna `actividades.imagen_origen_id`), y solo si no hay id en alguno de los dos lados cae a título equivalente. Es a propósito: si el Ayuntamiento reedita el post y reordena o añade/quita fotos, el título por sí solo puede confundir dos actividades parecidas ("Torneo de Pádel" / "Torneo de Pádel Infantil" son "equivalentes" para `titulosEquivalentes()` por contención) — el id no cambia con el post, así que desambigua siempre que el actor de Apify lo dé. `idDeFotoCarrusel()` prueba varios nombres de campo (`id`, `shortCode`, `pk`) por si el actor cambia; si ninguno está, o la fila es de antes de este campo, el título sigue siendo el único criterio disponible (limitación conocida, no nueva). El emparejamiento de la fila en sí (`idDeHija`, qué `origen_externo_id` reutilizar) sigue siendo por título a propósito — ver el comentario en `api/sync-instagram-noticias.js` — y comparte ese mismo riesgo de colisión; no se ha tocado en este cambio.

**Orden a seguir tras una pausa de Blob** (el store en sí se reactiva aparte, en el dashboard de Vercel — plan/facturación, fuera de este repo; esto es la secuencia de código): (1) desplegar este código (la lectura de Neon antes de subir es lo que evita que la cadencia normal de Apify vuelva a agotar la cuota); (2) `npm run rellenar:imagenes -- --dry-run` para ver cuántas filas se quedaron sin imagen durante la pausa (no llama a Blob, así que se puede correr aunque el store siga pausado); (3) `npm run rellenar:imagenes` (sin `--dry-run`) **por tandas** — respeta `--limite` (100 por defecto) para no volver a golpear la cuota de golpe justo después de recuperarla, repitiendo hasta vaciar el pendiente; (4) solo entonces reactivar la cadencia normal de Apify (el schedule/webhooks). Si Apify se reactiva antes del paso 1, el primer run se encuentra con todas las filas de la pausa a la vez e intenta subirlas de golpe.

### Data layer (`src/data/*.json`)

Static JSON is still the store for the read-only content below (events, news, directory, transit).

- `comercios.json` — **generated**, regenerate with `npm run fetch:comercios` (Google Places API scoped to Navalcarnero). Do not hand-edit.
- `servicios-locales.json` — hand-curated directory entries (municipal guide) **not covered by Google Places** (plumbers, renovation services, small trades). Rendered by concatenating it with `comercios.json` in `Mapa.jsx`, with **no dedup** — so an entry that also exists in Places would show twice.
- **Absorción curado → Places** (`scripts/fetch-comercios.mjs`, fase 1b + fase 4): the generic text queries never reach these businesses (each `searchText` caps at ~60 results ranked by prominence), so the script searches **each curated entry by name+address** and, when Places confirms it, the Google ficha **wins** (it brings coordinates, opening hours, ratings — the curated one has `lat/lng: null` and is therefore invisible on the map) and the `local/…` entry is **deleted** from `servicios-locales.json`. Measured hit rate: ~60 % of the curated entries exist in Places. Details that matter:
  - **Matching requires corroboration**, never just the name: identical phone, or same name + same street/number. Name-only similarity produced a real false positive ("Golden Consultores" ↔ "A&R Consultores"), hence `simNombre()` divides by the *longer* side when only one token matches. Two **different** phone numbers veto an absorption (they're the strongest signal of two different businesses) and send the pair to `duplicados-detectados.json` for manual review instead. Confidence ≥ 2 absorbs; 1 only reports.
  - **What survives from the curated entry**: its `categoria`/`subtipo` (the municipal guide classifies by hand — `frutas_y_verduras`, `comida_preparada` — where Places returns generic types like `point_of_interest,service`) plus any contact field Google left empty. They travel to `comercios-overrides.json`, which is the only thing reapplied on future regenerations. An existing panel override wins over the guide **unless it left the entry in a generic bucket** (`SUBTIPOS_GENERICOS` = `shop`/`service`): that isn't a decision, it's the type-mapping fallback, and the guide does know that "José Avelino Del Casar González" is Avelino's fishmonger. The reverse never happens either — a specific classification is never traded for a generic one from the guide.
  - **Phase 1b seeds the run with the current `comercios.json`** so a regeneration can't lose businesses. Text Search returns ~60 results per query ranked by prominence and that ranking **shifts between runs**: two regenerations on the same day dropped 25 previously-published fichas (Mercado de la Cruz Verde among them). Every existing `gpl_` id is re-queued for the phase-2 detail call, which is the only thing allowed to drop it (permanently closed, outside the municipality, no coordinates). Seeding also feeds the free name/phone matching of phase 1c, so it saves searches rather than costing them.
  - Absorption only happens if the matched `gpl_` entry **survived** phase 2 (not permanently closed, inside the municipality, not excluded by an override); otherwise the curated entry stays.
  - Deletion is safe because ids are only referenced by `destacados.referencia_id` / `organizaciones.comercio_id`, and those were checked to hold no real `local/…` values (July 2026). **If that changes, re-check before running** — an absorbed id breaks those references silently.
  - Audit trail in `servicios-absorbidos.json` (gitignored); to undo, `git checkout` the two JSONs. Flags: `--dry-run` (reports only), `--solo-servicios --limite-servicios=N` (test the linking alone, implies dry-run), `--sin-servicios` (skip the paid per-curated search).
- `eventos.json` — hand-curated event agenda (municipal + neighborhood).
- `eventos-externos.json` — **generated**, regenerate with `npm run fetch:eventos` (pulls from the Teatro TYL TYL WordPress "The Events Calendar" API + Ayuntamiento cultura RSS). The UI and assistant merge this with `eventos.json`. Also updated automatically via a Vercel Cron Job (see **Automatic event sync** below).
- `noticias.json` — **generated**, regenerate with `npm run fetch:noticias` (pulls from Ayuntamiento press RSS feed at `https://navalcarnero.es/navalcarnero/prensa/feed/`). Contains title, date, summary, full content, URL, and author for each news item. Used by Noticias page and assistant's knowledge base. **Auto-updated daily by the `sync-events` cron** (see **Automatic event sync**), so it no longer goes stale; the fetch/parse logic lives in the shared `api/_noticias-feed.js` (`obtenerNoticiasPrensa()`), imported by both the script and the cron.
- `horarios-bus.json` — **generated**, regenerate with `npm run fetch:transporte` (CRTM GTFS data). Bus line data with schedules.

### Instagram sync (webhook de Apify)

`api/sync-instagram.js` (Node — Anthropic SDK + `@vercel/blob` no funcionan en Edge) convierte los posts de Instagram de **cultura_navalcarnero** en eventos de la agenda. **No toca el cron diario**: los eventos van a Neon, no a `eventos-externos.json` (que el cron regeneraría y pisaría).

- **Disparador**: un webhook de Apify al terminar su scrape semanal (`POST /api/sync-instagram`). Auth como el cron: `Authorization: Bearer <INSTAGRAM_SYNC_SECRET>` (o `?secret=`, más cómodo en la config de Apify), comparación en tiempo constante, **falla cerrado** sin la env. El cuerpo puede ser el payload estándar de Apify (`resource.defaultDatasetId` → se descarga el dataset de su API con `APIFY_TOKEN`) o, para pruebas, un array de posts directo / `{posts: []}`. **Corte por antigüedad**: `esPostReciente()` (`api/_instagram.js`, `MAX_DIAS_ANTIGUEDAD = 30`) descarta antes de llamar a Claude los posts con `timestamp` de más de 30 días — cada run de Apify reenvía sus ~50 posts más recientes incluidos los de runs anteriores, y sin este corte se re-analizaban (coste de tokens) y re-subían sus imágenes cada día. Un post sin `timestamp` parseable **no** se descarta (para no romper el reproceso manual de posts de prueba sin esa fecha); el contador `descartadosPorAntiguedad` del resumen refleja cuántos se filtraron.
- **Extracción con Claude** (`claude-opus-4-8`, override `ANTHROPIC_MODEL`, structured outputs con `output_config.format`): identifica los posts que anuncian un evento real — caption con **fecha, hora y lugar** explícitos, y además un **acto al que se asiste** (función, concierto, fiesta, mercado, carrera). Fecha+hora+lugar NO basta: el prompt descarta explícitamente inscripciones, bases de concursos, **campañas y servicios aunque tengan fecha y hora** (donaciones de sangre, sorteos comerciales, custodia de llaves), **horarios de temporada** (piscina), noticias y actos fuera de Navalcarnero — sin esas exclusiones el webhook creaba "eventos" como el sorteo del comercio local o la temporada de piscina. Las fechas relativas ("este sábado 18") se resuelven con el `timestamp` del post. La salida se re-valida en servidor (regex de fecha/hora, categoría contra la taxonomía, shortCode contra los posts enviados) — nunca se confía en el modelo. **Subcategoría de cultura**: si `categoria = 'cultura'`, Claude devuelve además `subcategoria` (`teatro|cine|musica|danza|exposicion|otros`, whitelist `SUBCATEGORIAS_CULTURA` en `src/lib/eventos.js`, importada por este handler); fuera de cultura o fuera de la whitelist queda NULL. No son categorías hermanas a propósito: `cat:cultura` (push), los filtros y el perfil de las orgs siguen funcionando como paraguas — la subcategoría solo alimenta los **sub-chips de la página Eventos** (visibles con el filtro Cultura activo). Los eventos del TYL TYL se fijan a `subcategoria: 'teatro'` sin IA (en `api/sync-events.js` y `scripts/fetch-eventos.mjs`); los del RSS de cultura del Ayuntamiento no llevan subcategoría.
- **Imagen**: la primera foto del post se descarga y se sube a Blob en `instagram/<shortCode>.<ext>` (`addRandomSuffix: false` + `allowOverwrite: true` — re-runs sobrescriben, no acumulan), porque las URLs del CDN de Instagram van firmadas y caducan. **Cartel del carrusel (`indiceCartel`)**: si la extracción indica que los datos salieron del alt de una foto concreta del carrusel (marcada `[Imagen N]`), se sube ESA foto con sufijo `-c<i>` (`instagram/<shortCode>-c<i>.<ext>`) en vez de la portada; las fotos del carrusel viajan dentro del evento validado (`ev.carrusel`, resuelto en `validarExtraccion` — la variable `post` no existe en el scope del bucle de upsert, referenciarla ahí fue un ReferenceError real hasta ago-2026). Fallo de imagen ⇒ evento sin foto, nunca descartado (`subirImagen` atrapa cualquier error, incluida una cuota de Blob agotada o el store pausado, y devuelve `null`); en el UPDATE se conserva la imagen previa si esta vez falló. **Cuota de Blob**: antes del bucle de upsert se hace una sola consulta a `eventos_usuario` por los `origen_externo_id` asignados (`imagen_url`) — si la fila ya existe con imagen **coherente**, se reutiliza esa URL sin llamar a `subirImagen` (contador `imagenesReutilizadas`). Coherente significa: si la extracción señala un cartel, la imagen guardada debe ser un cartel (`-c<i>` en el nombre del blob, cualquier índice — el índice exacto que devuelve el modelo varía entre runs y exigir coincidencia haría flapear la foto y un `put()` por re-scrape); una **portada** guardada en una fila que debería llevar cartel se corrige con una única subida y desde ahí vuelve a reutilizarse. Sin cartel se reutiliza lo que haya; solo se sube si el post es nuevo o si `imagen_url` quedó a `NULL` (reintento). Ver **Presupuesto de Vercel Blob** más arriba.
- **Upsert en `eventos_usuario`**: clave `origen_externo_id` (columna + índice único parcial en `db/schema.sql`; el endpoint también los asegura inline, idempotente). El UPDATE no toca `estado` (un evento archivado a mano no resucita, un borrador publicado no vuelve a borrador) ni `notificado_en` (las ediciones no re-notifican). **Carruseles multi-evento** (`asignarIdentidades()`, ago-2026 — antes `validarExtraccion` admitía UN evento por shortCode y tiraba el resto como "validación de la extracción"; el dedup interno ahora es por post+fecha+título normalizado): un post con UN evento validado (el caso normal) sigue igual — id `ig-<shortCode>`, nace `publicado` con `notificado_en NULL` ⇒ **el digest push diario lo anuncia solo**. Un post con VARIOS eventos (p. ej. la programación deportiva: 10 carteles, 6-7 extracciones) da a cada uno un id propio `ig-<shortCode>-<slug del título>` (mismo patrón anti-reordenación que las hijas del webhook de noticias) y **nacen `borrador`** ⇒ se validan a mano en `/admin` → **Pendientes** y no entran en agenda ni en el digest hasta publicarse (publicar deja `notificado_en NULL`, así que el siguiente digest los anuncia). Si ya existe una fila del MISMO post con título equivalente (la histórica `ig-<shortCode>` o una hija cuyo título derivó entre extracciones — "Torneo de pádel" vs "Torneo de pádel Fiestas Patronales"), se **reutiliza su id** respetando su estado, en vez de crear una casi-duplicada; el emparejamiento es solo por título (aquí no hay `imagen_origen_id`), con el riesgo de colisión ya documentado en el webhook de noticias. **Dedup Neon↔Neon en servidor**: antes de insertar un candidato NUEVO se compara con los eventos ya existentes en esa fecha (misma fecha + `titulosEquivalentes` de `src/lib/dedupEventos.js`) y, si hay gemelo de OTRO post, se omite (`duplicadosOmitidos`) — el mismo acto anunciado en dos posts (la final del Mundial salió 4 veces) creaba una fila y un push por post. Las filas del propio post están exentas de ese gemelo (su identidad ya la resolvió `asignarIdentidades`, y dos hermanos de carrusel con títulos "equivalentes" por contención suelen ser actos distintos: pasan como borrador y decide la validación humana). El dedup con los eventos estáticos sigue siendo client-side a propósito (ahí la fila de Neon aporta la foto). **Trade-off aceptado**: los mismos carteles de un carrusel deportivo pueden existir además como filas de `actividades` (webhook de noticias, hijas `-img-<id>`); no hay dedup cruzado eventos↔actividades — ambos flujos pasan por Pendientes o por el superadmin, que es quien arbitra qué se publica.
- **Atribución por autor**: `ORG_POR_USUARIO` mapea el `ownerUsername` del post a una organización auto-provisionada con `ON CONFLICT (slug)` — `cultura_navalcarnero` → **"Cultura Navalcarnero"** (slug `cultura-navalcarnero`), que es también el fallback para coautores sin entrada propia, y `ayuntamientonavalcarnero` → **"Ayuntamiento de Navalcarnero"** (slug `ayuntamiento`, el mismo de `ORG_POR_FUENTE`/`ORGANIZADORES_FIJOS` en `temasPush.js`, así el tema `org:ayuntamiento` del selector de avisos cubre también estos eventos). Gracias al JOIN de `GET /api/eventos`, los eventos salen con `origen: 'cultural'` y `fuente` = nombre de la organización ("Organiza" en la ficha) sin tocar el endpoint público; el `DO UPDATE` del upsert re-atribuye `organizacion_id` si el mapa cambia. La org aparece como organizador suscribible (tema `org:cultura-navalcarnero`) en el selector de avisos, como cualquier org activa.
- **Env vars**: `INSTAGRAM_SYNC_SECRET` (obligatoria), `APIFY_TOKEN` (para leer el dataset del webhook), más las ya existentes `ANTHROPIC_API_KEY`, `DATABASE_URL` y la credencial de Blob. Todas en `VARIABLES_API` de `vite.config.js`.
- **Helpers compartidos** — `api/_instagram.js` (solo Node, usa `@vercel/blob`): `obtenerPosts` (payload Apify/array directo), `normalizarPost`, `primeraImagen`, `todasLasImagenes`, `shortCodeDe`, `subirImagen(prefijo, shortCode, url, sufijo = '')` y las constantes de límites. Los usan este webhook y el de noticias. **Robustez entre actores**: `shortCodeDe(post)` usa el campo `shortCode` si viene, y si no lo **deriva de la url** (`/p/<code>/` o `/reel/<code>/`) — necesario porque `apify/instagram-post-scraper` en modo Basic no devuelve `shortCode`; `primeraImagen` prueba `images[0]`/`childPosts[0].displayUrl`/`displayUrl`/`imageUrl`/`thumbnailUrl`/`image`, y `todasLasImagenes` hace el mismo baile pero devolviendo **todas** las fotos del carrusel (un post "Sidecar" puede traer una foto por instalación, cada una con su propia información) en vez de solo la primera; con `sufijo` no vacío, `subirImagen` sube a `<prefijo>/<shortCode>-<sufijo>.<ext>` en vez de `<prefijo>/<shortCode>.<ext>` — así el resto de fotos de un carrusel no chocan con el nombre de blob histórico de la primera. **El campo `alt` del post (descripción automática de la imagen que genera Instagram) viaja a Claude junto al caption en ambos webhooks**: los carteles municipales suelen llevar fecha/hora/lugar solo en la imagen (el caption es la sinopsis), y sin el `alt` esos posts no se reconocerían como eventos. **Matiz de los carruseles**: en un post "Sidecar" el `alt` del padre es siempre la fórmula genérica de Instagram ("Photo by X on <fecha>.") sin ningún dato del cartel — el contenido real vive en el `alt` de cada foto (`childPosts[].alt`). `normalizarPost` no manda el `alt` del padre a pelo: construye el que llega a Claude uniendo el del padre (si dice algo) con el de cada hija marcado `[Imagen N]` (N = su posición real en el carrusel, para que un hueco no desplace la numeración), descartando la fórmula genérica y con tope de 10 fotos / ~4000 caracteres. Sin esto, los carteles interiores de un carrusel municipal (p. ej. una programación con una actividad por foto) eran invisibles para la extracción — es la causa de que esos posts no generaran nada. En un post de foto única el resultado es idéntico a antes.

### Noticias de Instagram (ayuntamientonavalcarnero) + alertas urgentes + actividades

`api/sync-instagram-noticias.js` (Node, mismo molde que el de eventos) convierte los posts de Instagram municipales en **noticias**, **alertas urgentes** y **actividades** (triaje de tres vías, ver abajo). Van a **Neon, no a `noticias.json`**: una alerta ("corte de agua ahora") no puede esperar al ciclo commit→redeploy que regenera los JSON. El RSS de prensa sigue igual (`npm run fetch:noticias`).

- **Disparador**: un webhook de Apify → `POST /api/sync-instagram-noticias`. Auth idéntica al otro webhook pero con secreto propio **`NOTICIAS_SYNC_SECRET`** (rotación independiente; `Bearer` o `?secret=`, tiempo constante, **falla cerrado**). Mismo soporte de payload (dataset de Apify vía `APIFY_TOKEN`, o array directo / `{posts: []}` para pruebas). Mismo corte por antigüedad que el otro webhook (`esPostReciente()`, 30 días, `descartadosPorAntiguedad` en el resumen).
- **Montaje en Apify (operativo)**: noticias y eventos comparten el **mismo actor `apify/instagram-scraper`** (el que devuelve `shortCode` + `displayUrl`/`images`, es decir, fotos), pero como **dos tasks separadas**, cada una con su input, sus webhooks **a nivel de task** y su schedule: `eventos-cultura` (perfil `cultura_navalcarnero` → **dos webhooks**: `/api/sync-instagram` con `INSTAGRAM_SYNC_SECRET` y `/api/sync-instagram-noticias` con `NOTICIAS_SYNC_SECRET`, lunes) y `noticias-instagram` (perfil `ayuntamientonavalcarnero` → los mismos dos webhooks, diario). Cada cuenta dispara ambos endpoints porque los dos perfiles publican contenido de los dos tipos: el Ayuntamiento también anuncia eventos de agenda (cine de verano) y cultura también abre plazos de inscripción a talleres (actividades) — los prompts son complementarios (eventos exige fecha+hora+lugar y descarta inscripciones; noticias/actividades descarta eventos puntuales), así que un mismo post no acaba duplicado en ambas tablas. ⚠️ **Operativo pendiente**: el segundo webhook de la task `eventos-cultura` (→ `/api/sync-instagram-noticias`) hay que añadirlo en la config de Apify. **Los webhooks van en la task, nunca a nivel de actor** — un webhook de actor se dispara para *todas* sus tasks y cruzaría los flujos de las dos tasks.
- **Extracción con Claude — triaje de tres vías** (mismo modelo/override, structured outputs): cada post relevante se clasifica en `tipo`: **`noticia`** (información municipal; puede ser además alerta urgente) o **`actividad`** (algo a lo que APUNTARSE: inscripciones a talleres, cursos, campamentos, escuelas deportivas, ayudas, becas, empleo público — con `categoria` de la whitelist `deporte|talleres|infantil|mayores|educacion|ayudas|empleo|general` y `fechaLimite` YYYY-MM-DD si el post indica plazo). Los eventos de agenda puntuales se siguen descartando (los cubre `sync-instagram`), **pero un plazo de inscripción a una actividad continuada NO es un evento**: es `actividad` (antes se diluía en noticias). **Criterio editorial (ago-2026): utilidad práctica** — los servicios municipales (objetos perdidos, custodia de llaves, donaciones de sangre) y las campañas con información práctica (el sorteo "Yo compro en Navalcarnero") SÍ son noticias; solo se descartan felicitaciones, efemérides y teasers/promoción sin ningún dato usable. `urgente=true` solo si afecta AHORA a seguridad o servicios; `tipo_alerta` de la whitelist `incendio|corte_agua|corte_luz|trafico|emergencia|general`; `expiraEn` extraído del caption resolviendo relativos con el `timestamp` del post. Re-validación server-side: coherencia urgente⇔tipo_alerta⇔expira_en (CHECK `alerta_coherente`), **una `actividad` nunca es urgente** (el servidor fuerza `urgente=false`) y `categoria`/`fecha_limite` solo aplican a actividades (NULL en noticias), whitelists, truncados, shortCode contra los posts enviados. **Fallbacks**: alerta urgente sin fin conocido ⇒ `expira_en = publicado + 24 h`; actividad con categoría fuera de whitelist ⇒ `general`; sin plazo parseable ⇒ `fecha_limite NULL` (visible mientras siga en la ventana de historial).
- **Programaciones enlazadas (HTML y PDF) → borradores con validación humana**: se sigue el enlace del caption cuando el post fue triado `actividad` **o** cuando el triaje marcó `programaEnlazada=true` (el post remite a una programación/agenda en el enlace — p. ej. "descarga la agenda 👇 <PDF>"). Allowlist de dominio a propósito (`navalcarnero.es`, nada más), `AbortSignal.timeout` de 15 s. `descargarDocumento()` clasifica por content-type: **HTML** (máx 50 KB → galerías vía JSDOM + Claude, solo actividades — las pruebas deportivas participativas, torneos/carreras/marchas aunque la inscripción sea el mismo día, SON actividades con `fechaLimite` = día de la prueba, decisión ago-2026) o **PDF** (máx 15 MB → documento completo a Claude vía `extraerDeDocumento()` en `api/_actividades-parser.js`, que devuelve **eventos de agenda Y actividades**). **Todo lo extraído de un documento nace `borrador`** (un fallo de extracción son decenas de items): actividades en su tabla y eventos en `eventos_usuario` (org del autor del post, con dedup por fecha+título equivalente contra los ya existentes). **Ids de hijas por SLUG del título** (`ig-<shortCode>-<slug>`, `sufijoDe()`): con índices numéricos el orden de extracción cambiaba entre runs y el upsert machacaba una fila con el contenido de otra. **Fallback de carrusel CON VISIÓN**: si el documento no da actividades (o no hay enlace) y el post triado `actividad` es un carrusel, `extraerDeCarrusel()` saca una actividad por cartel **leyendo las imágenes** (cada `childPost` viaja como bloque `image` base64 a Claude; el `alt` —OCR de Instagram, a menudo incompleto o vacío— va de apoyo y como único dato si la descarga falla). Devuelve también `descripcion` (edades, precio, cómo inscribirse, teléfono) que las hijas guardan en `actividades.descripcion`. La foto de cada cartel se sube a Blob (`-c<i>`) — salvo que ya exista una hermana con esa misma foto (emparejada por `imagen_origen_id`, o por título si no hay id disponible — ver **Presupuesto de Vercel Blob** más arriba) con imagen guardada: entonces se reutiliza la suya sin volver a descargarla ni subirla. Igual con la foto del propio post (`imagenPost`, fallback de las hijas sin imagen): se reutiliza si CUALQUIER fila ya existente de ese `shortCode` tiene imagen, y solo se sube si es la primera vez o si quedó a `NULL`. **Guarda de la fila única**: si el mismo post ya creó un evento de agenda (`ig-<shortCode>` en `eventos_usuario`), la "actividad" del triaje se omite — era el mismo acto mal clasificado (el cine de verano). La actividad del propio triaje (caption, alta confianza) sigue naciendo `publicado` como fila única `ig-<shortCode>` si el documento no dio hijas. Al terminar un run con borradores nuevos se avisa al superadmin **por email (Resend, `enviarEmailPendientes` en `api/_email.js`, fail-soft)** — aviso que hoy comparten **las tres vías que crean borradores** (ver **Validación de pendientes**); se validan en `/admin` → **Pendientes** (ver abajo). La imagen de fallback es el blob ya subido de la foto del post, nunca la URL cruda del CDN de Instagram (caduca). Fallos no rompen el webhook (se loguean).
- **Validación de pendientes** (`api/super/pendientes.js` + `TablesPendientes.jsx`, pestaña "Pendientes" de `/admin` con contador): GET lista los borradores auto-sincronizados (eventos con `origen_externo_id IS NOT NULL` — los borradores de las orgs en su panel quedan fuera del alcance), PATCH publica, DELETE **archiva sin borrar** (`estado='archivado'`): como los upserts de los webhooks no tocan `estado`, un descartado no resucita al re-sincronizar. Publicar un evento lo deja con `notificado_en NULL` ⇒ el digest push del cron lo anuncia como a cualquier otro. Aquí caen los borradores de tres orígenes: hijas de documento/carrusel de este webhook, eventos de agenda extraídos de documentos, y desde ago-2026 los **eventos extra de un carrusel multi-evento del webhook de eventos** (`sync-instagram`, ver su sección). **Aviso por email en las tres vías que crean borradores** (`enviarEmailPendientes` en `api/_email.js`, siempre en try propio, fail-soft, solo con las filas realmente INSERTADAS ese run — un re-run no re-avisa): este webhook de noticias, `sync-instagram` (hijas de carrusel multi-evento) y los deportes a revisión del cron (`sync-events.js` con las `filasCreadas` de `upsertDeportesEnRevision`). Cada vía pasa su propia frase `origen` para la plantilla; la plantilla omite la sección de eventos o de actividades si va vacía, así que una vía que solo aporta un tipo no muestra "0" del otro. Los borradores que las orgs crean a mano en `/panel` no avisan a propósito (no son ingesta ni pasan por esta bandeja).
- **Tablas separadas** (nuevo, ver `ACTIVIDADES_SCRAPING.md`):
  - **`noticias_instagram`**: solo noticias + alertas urgentes (`tipo='noticia'`). Columnas: `titulo`, `resumen`, `cuerpo`, `urgente`, `tipo_alerta`, `expira_en`, `imagen_url`, **`imagenes_url`** (jsonb, array de URLs de Blob en el orden del carrusel — `imagenes_url[0]` es siempre la misma URL que `imagen_url`; `NULL` en filas antiguas o posts de imagen única). Imagen a Blob en `instagram-noticias/<shortCode>.<ext>` (primera foto) y `instagram-noticias/<shortCode>-<n>.<ext>` (resto del carrusel, `n` = índice desde 1), hasta `MAX_IMAGENES_POST = 6` por post (bajado de 12 — cubre la práctica totalidad de los carruseles municipales con menos coste de cuota de Blob y de tiempo de función). Se sube **solo si la noticia es nueva o su `imagen_url` está a `NULL`**: si ya existe con imagen, se reutiliza también su `imagenes_url` guardada (la galería se trata como un bloque, no foto a foto) sin pedir ninguna a Instagram; las subidas de un mismo post se paralelizan, nunca entre posts distintos.
  - **`actividades`**: actividades con plazo de inscripción o participativas — de documentos enlazados (`ig-<shortCode>-<i>`, nacen `borrador`) o del propio triaje (`ig-<shortCode>`, nace `publicado`, con `descripcion` = resumen del triaje). Columnas: `titulo`, `descripcion`, `categoria`, `fecha_limite`, `horario`, `lugar`, `imagen_url`, **`imagen_origen_id`** (id estable de la foto de origen dentro del carrusel, NULL fuera de un carrusel — ver **Presupuesto de Vercel Blob**), `url_fuente`, **`estado`** (`borrador|publicado|archivado`). Imagen a Blob en `instagram-actividades/<shortCode>.<ext>`. Sin galería (`api/sync-instagram.js`, el webhook de eventos, tampoco la lleva: eventos y actividades se quedan con una sola foto a propósito, fuera del alcance de esta funcionalidad).
- **`GET /api/noticias-instagram`** (Edge, público, cache CDN 60 s, `{noticias: []}` con 200 si Neon cae): últimos 60 días / **100 items**. Retorna solo noticias + alertas (no actividades). Cada item replica el shape de `noticias.json` más `imagen`, **`imagenes`** (array de URLs, siempre `[]` en vez de `null` — así la UI no tiene que defenderse), `urgente`, `tipoAlerta`, `expiraEn`, `origen: 'instagram'`.
- **`GET /api/actividades`** (Edge, público, cache CDN 60 s, `{actividades: []}` con 200 si Neon cae): actividades **`publicado`** vigentes ordenadas por `fecha_limite ASC` (las que cierren primero primero), `LIMIT 100`. Vigencia: `fecha_limite >= hoy`, o **sin plazo conocido, publicadas hace ≤ 45 días** (`DIAS_SIN_PLAZO` — sin ese corte una fila con `fecha_limite NULL` sería visible para siempre). Fechas con `to_char` (convención del proyecto). Retorna: `titulo`, `categoria`, `fecha_limite`, `horario`, `lugar`, `imagen_url`, `url_fuente`, `publicado_en`.
- **`src/lib/useNoticiasPublicas.js`**: mezcla RSS + Neon, **descarta lo de más de un mes** (`fecha >= hoy − 1 mes`, filtro de presentación — el RSS arrastra items de años atrás; no borra nada, y los avisos vigentes se calculan aparte y no dependen de este corte) y **ordena por fecha desc** (sin el sort, la lista de Noticias no intercalaría bien las de Instagram). Expone `noticias` (solo noticias + alertas, excluye actividades), `alertas`, `ETIQUETAS_ALERTA`. **Sin dedup RSS↔Instagram** (trade-off aceptado: la misma noticia puede salir dos veces con ids distintos).
- **Actividades consolidadas en la agenda `/eventos`**: Las actividades con plazo de inscripción (del scraper de Instagram via `api/sync-instagram-noticias.js`, tabla `actividades` en Neon) se muestran como eventos con **su categoría real de Neon** (`a.categoria`, el CHECK de la tabla: `deporte|talleres|infantil|mayores|educacion|ayudas|empleo|general` — las 8 tienen entrada en `CATEGORIAS_EVENTO` de `src/lib/eventos.js`, así que todas son filtrables; antes se forzaban todas a `talleres`). Se integran automáticamente en `/eventos` mediante `useEventosPublicos()`, que mapea actividades a eventos. La página `/actividades` fue eliminada; el enlace "volver" del detalle de una actividad (`NoticiaDetalle`) lleva a `/eventos?categorias=<su categoría>`.
- **Lista con scroll infinito** (`Noticias.jsx`): muestra lotes de `LOTE = 8` y revela otro lote cuando un centinela al final entra en pantalla (`IntersectionObserver`, `rootMargin 200px`). Todo en cliente — el hook ya trae todas las noticias en memoria, sin peticiones extra. Tarjeta estilo periódico: foto a sangre arriba (real de Instagram, o fallback de degradado + trama con icono para las del RSS, vía `cartelDe`).
- **Avisos del municipio (los `urgente`) — sección propia, SIN push**: los posts que Claude marca `urgente` (cortes de calle/agua/luz, incendios, emergencias) **no** se mezclan con las noticias; van a una sección "Avisos" separada, visible para todos (sin suscripción). `useNoticiasPublicas` expone `alertas = deLaBase.filter(n => n.urgente && n.expiraEn && Date.parse(n.expiraEn) > Date.now())` (vigentes; al caducar `expira_en` desaparecen, sin cron). ### Notificaciones push (fase 1 — anónima por temas)

Implementa la fase 1 de `NOTIFICACIONES_PUSH.md` (Web Push estándar con VAPID, sin Firebase). Suscripción **anónima por dispositivo**, sin cuenta: una fila en `push_suscripciones` (`endpoint` UNIQUE, claves `p256dh`/`auth`, `temas` jsonb, `usuario_id uuid NULL` reservado para la fase 3, en `TABLAS` de `api/_db.js`).

- **Temas**: lista plana `todos` | `cat:<categoria>` | `org:<slug>`. Todo el vocabulario vive en `src/lib/temasPush.js` (módulo "limpio" sin JSX/JSON, importado por Edge, Node y el navegador, como `tarifasDestacados.js`): lista blanca (`validarTemas`), etiquetado de eventos (`temasDeEvento`) y matching (`interseca`). **El matiz TYL TYL**: `ORG_POR_FUENTE` mapea fuente-externa → slug (`'TYL TYL'`→`tyl-tyl`, `'Ayuntamiento'`→`ayuntamiento`), y los eventos de Neon llevan `organizacionSlug` del JOIN, así que `org:tyl-tyl` cubre los dos caminos del teatro (API WordPress y panel). Los curados de `eventos.json` con `origen: 'municipal'` se atribuyen al Ayuntamiento; los `vecinal` no tienen organizador.
- **`POST/DELETE /api/push`** (Edge, sin auth — la suscripción es anónima): upsert por `endpoint` / baja. Defensas iguales al resto de mutadores públicos: CSRF por Origin, rate-limit por IP (`_ratelimit.js`, fail-open), validación estricta (endpoint https ≤1024, claves base64url, temas contra la lista blanca).
- **Envío** (`api/_push-send.js`, **solo Node**: `web-push` necesita el crypto de Node — jamás importarlo desde un handler Edge): `enviarDigest(eventos)` empareja suscripciones con eventos etiquetados, envía en lotes de 25 (`Promise.allSettled`), y **borra inline** la fila cuando el push service devuelve 404/410 (no hay cron de limpieza aparte). Devuelve `{configurado, enviadas, fallidas, caducadasBorradas, suscripciones, idsEntregados}`; nunca lanza por fallos individuales. `idsEntregados` = ids de evento que viajaron en **al menos un envío entregado** (fulfilled; los 404/410 caducados no cuentan) — es la señal que el llamador debe usar para marcar "ya avisado" evento a evento, porque los contadores agregados no dicen qué eventos iban en cada envío. Payload `{titulo, cuerpo, icono, url}`: personalizado con 1 evento, agrupado con varios.
- **Disparador — digest diario en el cron existente** (`api/sync-events.js`, paso 5, tras el commit a GitHub): etiqueta los `agregados` externos futuros + los eventos de Neon pendientes y llama a `enviarDigest`. Todo en try/catch: un fallo de push se loguea en `resultado.errores` y **nunca rompe la sincronización ni el commit**. **Decisión** (el documento daba dos opciones): los eventos de organizaciones (Neon) entran en **este mismo digest**, no se dispara nada al publicar desde `api/admin/eventos.js`; el estado "ya avisado" es la columna `eventos_usuario.notificado_en` (se avisan los `publicado` futuros con `notificado_en IS NULL` y el cron la rellena **solo para los eventos cuyo id está en `idsEntregados`** — es decir, solo si ESE evento llegó de verdad a algún suscriptor). **`configurado` no basta por sí solo**: solo dice que había claves VAPID; con 0 suscripciones, o con suscripciones cuyos temas no intersecan con un evento concreto, marcar igualmente "gastaba" el evento en silencio y el primer suscriptor real se encontraba la columna consumida sin que nadie hubiera recibido nada (bug corregido ago-2026; antes la condición era `configurado && deNeon.length > 0` y marcaba todos los `deNeon` en bloque). Un evento sin destinatario hoy queda en NULL y reintenta en digests futuros mientras siga siendo futuro. Así un borrador publicado tarde también entra y las ediciones no re-notifican. Al desplegar la feature se hizo un backfill manual de `notificado_en` sobre los ya publicados para no notificarlos como nuevos.

#### Bandeja de avisos (historial in-app)

Como Web Push es efímero, hay un historial navegable dentro de la app. Vive en la **cabecera global** (`src/components/avisos/CentroAvisos.jsx`, montado en `Header.jsx` en las barras móvil y escritorio), así que la campana está en **todas** las páginas públicas, no solo en Eventos.

- **Tabla `push_avisos`** (en `TABLAS`): una fila por evento anunciado en un digest — `referencia_id` (id público del evento, **UNIQUE**), `titulo`, `cuerpo`, `url`, `temas` jsonb, `enviado_en`. El cron (`api/sync-events.js`) inserta cada evento de `paraAvisar` con `ON CONFLICT (referencia_id) DO NOTHING` **antes** del envío y en su propio try, así la bandeja se puebla aunque no haya claves VAPID o el envío falle.
- **`GET /api/avisos`** (Edge, público, cache CDN 60 s, `{avisos: []}` con 200 si Neon cae): últimos 60 días / 50 avisos en crudo. El **filtrado por temas es client-side** (`src/lib/useAvisos.js` con `interseca`), mismo patrón que `useDestacados`: una respuesta cacheable para todos, sin exponer el `endpoint` ni multiplicar almacenamiento por suscriptor. **Trade-off aceptado**: la bandeja muestra "avisos que coinciden con tus temas", no "lo que exactamente recibió este aparato".
- **Estado leído/borrado — POR DISPOSITIVO** (las suscripciones son anónimas, no hay estado de lectura en Neon): dos listas de `referencia_id` en localStorage — `ncv_avisos_leidos` y `ncv_avisos_ocultos` (helpers en `push.js`, orquestados por `useAvisos`). **Borrar oculta el aviso solo en este aparato** (el feed global no se toca; el aviso sigue existiendo para los demás). `useAvisos` expone `marcarLeido`/`marcarNoLeido`/`marcarTodasLeidas`/`borrar`/`borrarTodas`, poda de localStorage los ids que ya no están en el feed, y migra el `ncv_push_visto` de la primera versión (avisos anteriores a esa marca → leídos) una sola vez.
- **UI**: `DialogoBandeja.jsx` distingue leídos (atenuados) de no leídos (resaltados, con punto), permite marcar/borrar por aviso y en bloque, y su **icono de ajustes** abre el diálogo de gestión de la suscripción (`DialogoAvisos`) — el mismo al que llega el botón "Recibir avisos" de Eventos. Abrir la bandeja **no** marca nada como leído (la lectura es explícita). Cada aviso enlaza a `/eventos/<id>` (y se marca leído al abrirlo). Sin suscripción, la bandeja va **vacía** y la campana sin contador (solo la invitación "Activar avisos"): un aparato que no ha activado los avisos no debe ver "notificaciones" que nadie le envió. El corte es solo de presentación (`useAvisos` devuelve `[]` si no hay suscripción — copia local de temas **o** suscripción push real vía `haySuscripcionReal()`); `/api/avisos` sigue siendo un feed público cacheable. Al desplegar se hizo un backfill de `push_avisos` con los eventos ya publicados+notificados para que la bandeja no naciera vacía.

### Open Graph dinámico por evento (`/eventos/:id`)

Un enlace a la ficha de un evento pegado en WhatsApp, Slack o un correo enseña **el título, la descripción y el cartel de ESE evento** en vez del logo genérico. El SPA sigue sirviéndose igual para los vecinos: la vista previa enriquecida solo se genera para crawlers.

- **Mecanismo: rewrite condicionado en `vercel.json`, no middleware.** El primer rewrite (debe ir **antes** del catch-all `/((?!api/).*)` → `/index.html`) enruta `/eventos/:id` a `/api/og-evento?id=:id` **solo si** la cabecera `user-agent` casa con la regex de `has`. Se eligió esto y no un `middleware.js` porque la decisión la toma la capa de routing de Vercel: un navegador normal no ejecuta ninguna función ni paga latencia, y una caída de la función no puede tumbar la ficha de un evento. El coste es que la lista de crawlers queda **duplicada**: la canónica en `api/_crawlers.js` (`CRAWLERS`/`PATRON_CRAWLER`, usada por el espejo de dev) y su copia serializada en `vercel.json`, porque un JSON no puede importar JS. **Si tocas una, toca la otra.**
- **Qué cuenta como crawler**: `whatsapp`, `facebookexternalhit`, `facebookcatalog`, `twitterbot`, `slackbot`, `slack-imgproxy`, `telegrambot`, `linkedinbot`, `discordbot`, `applebot`, `googlebot`, `bingbot`, `embedly`, `redditbot`, `pinterest`, `vkshare`, `skypeuripreview`, `whatsdog`, `mastodon`, `bluesky`, `signal`. El matching es **case-insensitive** (`(?i)` al principio de la regex de `vercel.json`): WhatsApp manda `WhatsApp/2.24.x` con mayúsculas y sin el flag no casaría. Ojo al ampliar la lista: `applebot` no debe convertirse en algo que cace el `AppleWebKit` de Safari — hay test de eso.
- **Por qué solo a ellos**: meter una función en el camino de toda visita a un evento añade latencia y un punto de fallo a la ruta más visitada de la app, y no aporta nada — el navegador pinta el título con React en cuanto arranca. El crawler, en cambio, **no ejecuta JS**: solo lee el HTML inicial, y por eso es el único que necesita los meta ya resueltos en servidor.
- **`api/og-evento.js`** (Edge; el driver de Neon va sobre fetch y el bundle de Edge sí incluye los JSON importados): resuelve el evento **repitiendo el mismo pipeline que `useEventosPublicos`** — `enriquecerPorCartel([...eventos.json, ...eventos-externos.json])` + `combinarEventos(estáticos, [...\/api\/eventos, ...\/api\/actividades])` + filtro de `/api/eventos-ocultos` —, y busca por `id` **o** por `idsSecundarios`. Reproducir el merge **no es opcional**: el cartel del voleibol vive en la fila de Neon y solo aparece tras fusionarla con el evento estático; un lookup por prefijo daría el logo genérico. Que OG y página muestren cosas distintas sería el bug.
- **Meta que emite**: `og:title` (título), `og:description`, `og:image`, `og:url`, `og:type=article`, `og:locale`, y los `twitter:*` en paralelo.
- **Prioridad de `og:description`** (decidida, no improvisar otra): **descripción propia** resumida a 200 chars cortando por palabra (nunca a mitad, que en la burbuja de WhatsApp canta) > **`lugar · fecha larga`** > el **literal genérico del `index.html`** (`Portal vecinal de Navalcarnero: …`). Nunca se deja vacía: sin descripción, WhatsApp pinta la burbuja con el título flotando. La rama de `lugar · fecha` lleva guarda de fecha ausente — `formatearFechaLarga(undefined)` lanza `Invalid time value`, y hay 21 eventos reales sin fecha.
- **Timeout y fail-soft (8 s)**: las tres llamadas a los endpoints propios y la lectura del `index.html` van con `AbortSignal.timeout(8000)`. Un origen que tarda o falla aporta lista vacía y el merge sigue con los demás; en el peor caso el evento no se encuentra y se sirve el `index.html` genérico. **El número salió de 3000 y se subió tras verlo fallar en preview**: con 3 s, la PRIMERA petición a un deploy nuevo se pasaba de largo (arranque en frío de esta función + de `/api/eventos` + conexión de Neon) y servía el logo genérico, mientras que la segunda ya traía el cartel. La primera petición de WhatsApp a un enlace recién compartido es exactamente esa, así que el caso degradado era el más probable en la práctica. 8 s cabe de sobra en la paciencia de un crawler (WhatsApp espera del orden de 10-20 s). **Ojo al bajarlo**: el síntoma es silencioso — vista previa genérica, ningún error en ningún log. **`twitter:card` es `summary_large_image` con cartel real y `summary` con el logo**; las dimensiones `og:image:width/height` solo se declaran para el logo, del que sabemos que es 1024², nunca para un cartel cuyo tamaño no conocemos sin descargarlo.
- **Imagen (opción A, decidida)**: sin `imagen` se cae al logo `https://<host>/logo.png`; no se genera nada al vuelo. Las **relativas se absolutizan** contra el origen — 42 eventos curados llevan `/img/eventos/…` y WhatsApp no resuelve rutas relativas.
- **Fallback silencioso**: id inexistente, no publicado u oculto por el superadmin ⇒ se devuelve el `index.html` tal cual con **HTTP 200, nunca 404** (el enlace puede estar pegado en un chat y tiene que seguir abriendo). Cualquier excepción cae al mismo sitio. El HTML se construye **partiendo del `index.html` real** que sirve el origen y sustituyendo sus meta, no de una plantilla propia: así los hashes de los assets del build nunca se quedan atrás.
- **Espejo en dev** (`vite.config.js`): `vercel.json` no se aplica con `npm run dev`, así que un middleware de Vite replica ese primer rewrite usando `esCrawler()`. Sin él, esto solo se podría probar desplegando. Es dev-only, no viaja a producción.
- ⚠️ **Lo único que no se puede verificar sin desplegar** es que Vercel acepte `(?i)` en `has[].value` (la doc lo documenta; el motor es RE2). Si no lo aceptara, el rewrite simplemente no dispararía y las vistas previas seguirían siendo las genéricas de hoy — degradación al comportamiento actual, nunca una página rota. **Comprobar en el primer deploy** con `curl -A "WhatsApp/2.24" https://ennavalcarnero.es/eventos/<id>`.
- ⚠️ **Ventana de cache: un evento recién publicado se comparte con la vista previa genérica durante ~1-2 min.** La respuesta lleva `s-maxage=60` y `/api/eventos` tiene otros 60 s de cache CDN, así que en el peor caso se encadenan (~2 min) antes de que el cartel aparezca en la burbuja. Si alguien reporta "he compartido el evento y sale el logo", la primera pregunta es cuánto hacía que lo publicó — reenviar el enlace pasado un par de minutos lo resuelve.
- **Por qué `s-maxage=60` y no 300 — decisión, no default.** La primera implementación puso 300 s; se bajó a 60 al documentar el punto anterior, porque la ventana aprobada era de ~60 s y 300 la quintuplicaba en silencio. **Es un cambio de comportamiento real, no cosmético**: con la mitad de TTL el CDN revalida ~5× más a menudo, así que una url caliente (un enlace que circula por varios grupos de WhatsApp) genera del orden de 5× más invocaciones de la Edge Function. Se acepta con el volumen previsto — son enlaces de un municipio, no tráfico de portada — a cambio de que un evento recién publicado se comparta con su cartel casi de inmediato. **Si el volumen creciera, este es el primer número que hay que revisar**, y subirlo a 300 solo empeora el retardo de la vista previa, no rompe nada.

### Buzón de sugerencias (formularios públicos)

New public suggestion system for residents to submit ideas, events, report bugs, and request new businesses to be added to the directory.

- **`src/pages/Sugerencias.jsx`** — main suggestions page (`/sugerencias`, linked in `MenuDrawer`). Flexible form with type selector: Idea, Evento, Comercio, Error. Type-specific required fields:
  - **Generic** (Idea/Evento/Error): `titulo` (required), `detalle` (required, 500 char visible limit), `email` (optional for reply).
  - **Comercio**: `nombre` (required), `tipoNegocio` (required, from `LISTA_CATEGORIAS`), `direccion` (required), `horarios` (required), `telefono` (optional), `foto` (optional, uploaded to Vercel Blob via `SelectorImagen`).
  - All forms include `recaptchaToken` (obtained from browser via `useRecaptcha()` hook before submission).
  - Confirmation screen on successful submit; fallback to `mailto:` if no `ENDPOINT` is configured.

- **`api/sugerencias.js`** — Edge Function POST endpoint (`/api/sugerencias`) that receives and validates suggestions. Workflow:
  1. **reCAPTCHA v3 verification** first (score 0.0–1.0; threshold 0.5). Returns 403 if score < threshold (bot detected).
  2. **Rate-limiting** by IP (max 5 per hour via `_ratelimit.js`). Returns 429 if exceeded.
  3. **Field validation** by `tipo`: commerces require `nombre`, `direccion`, `horarios`, `tipoNegocio`; others require `titulo`.
  4. **Logging** with type, IP, and timestamp; low scores logged for analysis.
  5. Returns 200 on success; 400/403/429 on failure.

- **`src/components/directorio/SugerirComercio.jsx`** — modal form ("¿Falta un comercio?" button in `/comercios`) now sends to `/api/sugerencias` instead of mailto (if `VITE_FORM_ENDPOINT` not overridden). Maps form fields (`categoria` → `tipoNegocio`) and includes `recaptchaToken` in payload.

- **`src/lib/useRecaptcha.js`** — React hook that dynamically loads the Google reCAPTCHA v3 script and exposes `getToken(action)` to obtain a verification token. Actions: `'sugerir_idea'`, `'sugerir_comercio'`. Token is always sent in the payload as `recaptchaToken`.

- **Environment variables**:
  - `VITE_RECAPTCHA_SITE_KEY` (public, loaded by browser; prefixed with `VITE_` so it's never in the backend bundle).
  - `RECAPTCHA_SECRET_KEY` (private, server-only; added to `VARIABLES_API` in `vite.config.js` for dev).
  - Test keys in `.env` work on `localhost` and `127.0.0.1`; in production, replace with real keys from https://www.google.com/recaptcha/admin.

- **Security layers**:
  1. reCAPTCHA v3 (invisible bot detection, score-based).
  2. Rate-limiting by IP (form spam prevention).
  3. CSRF protection via Origin validation.
  4. Server-side field validation (never trust client).
  5. Logging for suspicious patterns.

- **Future work**: store suggestions in DB (new `sugerencias` table), send admin email notifications, add a superadmin review panel in `/admin`.

### Reclamación y gestión de comercios + Botón compartir

Implementa el flujo completo para que dueños de comercios reclamen sus fichas, editen su perfil enriquecido, y la app sea compartible. Ver `IMPLEMENTACION_RECLAMACIONES.md` para detalles técnicos completos.

**Flujo:**

1. **Reclamación anónima** (`api/solicitar-reclamacion.js` — Node, POST público): Dueño rellena formulario sin auth. El campo debe viajar por el endpoint: mientras no se devolvía, la condición era siempre falsa y **ninguna** org veía la pestaña.

### Automatic event sync

- `api/sync-events.js` — Vercel Cron Job endpoint that runs **daily at 07:00 UTC** to fetch and sync events from external sources.
  - **Execution order** (ensures fresh data, no caching shortcuts):
    1. Fetch all events from external sources: TYL TYL API + Ayuntamiento RSS + Red de Teatros + Actividades Deportivas (RSS de deportes, `api/_actividades-deportes-feed.js`) + Fiestas Patronales 2026
    2. Combine events without duplicates and sort by date
    3. Read current `eventos-externos.json` from GitHub API
    4. Compare fetched events with the current version
    5. If changes detected, commit to GitHub via GitHub API
  - Accepts both GET (from Vercel Cron) and POST methods.
  - **Also regenerates `noticias.json`** (press RSS) in the same run: fetches the press feed via `obtenerNoticiasPrensa()` (`api/_noticias-feed.js`, article content fetched in batches so it doesn't blow the function time), compares against the current file's raw text, and stages it if it changed. Fail-soft in its own try — a noticias failure is logged in `errores` but never breaks the events sync or the push digest.
  - **Does not write to the local filesystem** — reads from GitHub API instead (avoids EROFS read-only filesystem in Vercel runtime). Both changed files (`eventos-externos.json` and/or `noticias.json`) go in a **single commit** via `commitArchivos()` (Git Data API, multiple blobs in one tree).
  - If the fetch fails for either source, logs the error but still commits (preserves any partial updates).
  - Returns a summary: `{ timestamp, agregados, actualizados, eliminados, estadisticas, commitRealizado, errores }` (`estadisticas.noticias` = count fetched).
  - Vercel detects the commit and redeploys automatically, at which point the new JSON becomes available on disk.
  - At the end of a successful run it inserts one row in `ingesta_log` (fuente `sync-events`) with the run's counters; the deportes feed logs its own `deportes` row from inside `obtenerActividadesDeportivas()`. See **Observabilidad de la ingesta** below.
- Cron job is configured in `vercel.json` as `{ path: "/api/sync-events", schedule: "0 7 * * *" }`.
- Requires environment variables: `GITHUB_TOKEN` (personal access token with repo write access), `GITHUB_REPO` (e.g., "user/naval-app"), and optionally `CRON_SECRET` (for validating cron calls from Vercel).
- **Bulk-load protection — principle and threshold**:
  - **Principle**: the digest announces new events one-by-one only when they are few; faced with any large load, automatic silence.
  - **Threshold**: if the total of new external events in a run exceeds 30, **all** of them are added to the notification history (`push_avisos` table) so users can discover them browsing the events feed, but they are **excluded from the push digest** to prevent notification avalanches and protect against feed breakages, one-time bulk data loads, or unexpected spikes.
  - **Mechanics**: Events are still grouped by source in logs and statistics to track provenance (useful for debugging), but the digest/bandeja decision is global — if total > 30, all externals go to bandeja; if total ≤ 30, all go to digest (alongside Neon events). This rule applies to all sources equally (TYL TYL, RSS, Red de Teatros, Fiestas, future sources) and scales naturally with new additions.
  - **Rationale**: choosing which subset of a large load to announce (e.g., "first 30 only") would be arbitrary and leave the user with an incomplete, confusing digest. Silence is honest: if something goes wrong or a source changes, the user sees nothing pushed but can still explore the full agenda.

### Fiestas Patronales 2026

`eventosFiestas()` (in `api/sync-events.js`) — loads pre-classified events from `api/_datos/programa-fiestas-2026.js` into the merged event stream. A **one-time static import** (not fetched from external API) of 158 hand-curated events for the annual municipality festival.

- **Source**: `api/_datos/programa-fiestas-2026.js` — ES module wrapping 158 events as JSON, each pre-annotated with `categoria` (deporte, cultura, infantil, fiestas, etc.), optional `subcategoria`, `esTaurino` flag, and `organiza` (event organizer name, e.g., "Ateneo de Navalcarnero", or empty for municipal/unattributed events). Module lives in `api/_datos/` to ensure it resolves at runtime in Vercel serverless (unlike `src/data/*.json`).
- **No heuristics**: fields are read directly from the JSON — no AI classification, keyword matching, or post-processing. The classification is final and user-verified.
- **ID stability**: events get stable IDs in the format `fiestas-<claveNorm(titulo)>-<fecha>` where `claveNorm()` normalizes the title to lowercase + hyphen-separated words (no accents/punctuation, max 50 chars) so deep links and subsequent cron runs recognize the same event. Example: `fiestas-copa-federacion-v-memorial-angel-carrizo-2026-08-19`.
- **High-volume protection**: with 158 events, this source **always** triggers the bulk-load rule — all fiestas events go to `push_avisos` but not to the push digest. This prevents a notification flood on day 1 while keeping them browsable in the events feed.
- **Fail-soft**: if JSON loading fails, the error is logged in `resultado.errores` and the sync continues with the other sources (TYL TYL, RSS, etc.); the cron never breaks. If the load succeeds but returns 0 events (module corruption), that is also logged as an error (silently losing 158 events is worse than a logged failure).
- **Image fallback**: events carry no `imagen` field — they fall back to `cartelDe()` category gradients (not generic stock photos) in the UI.
- **Fuente attribution**: events carry the actual organizer name from `e.organiza` (35 events) or empty string (123 events attributed to the municipality).

### Red de Teatros de la Comunidad de Madrid

`eventosRedTeatros()` (in `api/sync-events.js`) — loads pre-classified events from `api/_datos/red-teatros.js` into the merged event stream. A **manual semestral import** of ~4-8 cultural events from the Madrid regional theater network's Navalcarnero venue calendar. ⚠️ The runtime source is the **`.js` module** (the JSON travels inline in a template string, same pattern as `programa-fiestas-2026.js` so it resolves in Vercel serverless); `api/_datos/red-teatros.json` is a sibling copy — when updating the semester, edit the `.js` (or keep both in sync).

- **Source**: `https://www.madrid.org/clas_artes/red/navalcarnero.html` — public HTML page with listings by season (Teatro, Danza, Música, Público Familiar). Programación refreshes in June (2º semestre) and December (1º semestre).
- **Why manual, not scraped**: madrid.org datacenter IP-blocks Vercel function requests (HTTP 403), confirmed 2026-08-20. No User-Agent workaround. Automating via Apify proxy costs $30-50/month for 2 updates/year (4 events) — not sustainable. Manual copy matches the fiestas pattern (copy once → lives all semester).
- **Process**: When madrid.org updates (June/December), open the link above, copy the ~4-8 events' titles, dates, times, rooms, synopses (where available), cast, and image URLs. Paste them into `api/_datos/red-teatros.js` (inline JSON) following the existing schema. For incomplete fichas (only listing data, no detail page), leave `descripcion`, `interpretes`, `duracion`, `edadRecomendada` empty. No code changes needed — the cron picks them up automatically.
- **Schema** (`api/_datos/red-teatros.json`): array of events with `{slug, titulo, compania, categoria (always 'cultura' for theater — see below), subcategoria (teatro|danza|musica), publicoFamiliar (boolean, preserved for future UI use), fecha (YYYY-MM-DD), hora (HH:MM), lugar, url, imagen, imagenes (array), descripcion, interpretes, duracion, edadRecomendada}`. `eventosRedTeatros()` derives `id` (`redteatros-<slug>`) and `origen` itself — the `id` field some entries carry in the data is ignored.
- **Categorization rule**: All Red de Teatros events map to `categoria: 'cultura'`, regardless of audience (infantil/adultos). **Rationale**: "infantil" in this project means *activities you sign up for* (workshops, camps, ludotecas); theater is *performances you attend*, even if for children. If Red de Teatros labels a children's show "infantil" while TYL TYL labels equivalent children's theater "cultura", the same type of work would scatter across different filters depending on source. Solution: unify at `cultura` + use `publicoFamiliar` flag for future UI distinction (badges, separate rows, etc.). This keeps filtering consistent: all theater in one place, sorted by audience at presentation time, not by ingestion source.
- **Incomplete fichas**: Three events (En el viento, Martina y los Supersingers, La Gran Aventura del Pollo Pepe) have listing-only data; their detail pages are pending. Image URLs are deduced from the pattern and **not verified** — `eventosRedTeatros()` includes a fallback to `cartelDe()` gradient if image fetch fails.
- **Fail-soft**: if JSON is empty or malformed, the error is logged in `resultado.errores` and the cron continues; events simply don't appear that cycle (better than silently missing them due to scraper breakage).
- **Future work (deferred)**: When `publicoFamiliar` gets UI treatment (badge, sub-filter, etc.), backfill the TYL TYL catalog with the flag — almost all TYL TYL events are children's theater and should carry it.

### Observabilidad de la ingesta (`ingesta_log`)

Cada ejecución de un pipeline de ingesta de eventos/actividades deja una fila en la tabla `ingesta_log` (en `db/schema.sql` y en `TABLAS` de `api/_db.js`, así que el health la comprueba): `fuente`, `ejecutado_en`, `candidatos`, `emparejados`, `nuevos`, `descartados` y `descartados_por_motivo` (jsonb `{"motivo textual": cuenta}` — p. ej. `"duplicado por url"`, `"validación de la extracción"`, `"fin de plazo con actividad gemela"`). **Solo observabilidad, cero comportamiento**: los contadores ya existían en memoria en cada run; esto los persiste.

- **Helper**: `api/_ingesta-log.js` → `registrarIngesta({fuente, candidatos, emparejados, nuevos, descartados?, motivos})`. **Jamás lanza**: cualquier fallo (Neon caído, sin `DATABASE_URL`) se atrapa y queda en `console.error` — un fallo del log nunca rompe la ingesta. Asegura tabla e índice inline (idempotente, mismo patrón que `asegurarTablas` de los webhooks). Los motivos a 0 se omiten del jsonb; si no se pasa `descartados`, es la suma de los motivos.
- ⚠️ **Las columnas NO comparten unidad entre fuentes** — cada fuente cuenta lo que su pipeline maneja, y las cifras solo son comparables de una fuente **consigo misma** a lo largo del tiempo:
  - `sync-events` cuenta ítems de las 5 fuentes del cron, con **partición limpia**: `candidatos = emparejados + nuevos + descartados`.
  - `deportes` cuenta carteles, y `emparejados` es un subconjunto **DENTRO de** `nuevos` (los carteles que además enriquecen un evento del programa), no una categoría aparte — aquí NO sumar `candidatos = emparejados + nuevos + descartados` (la identidad es `candidatos = nuevos + descartados`).
  - `sync-instagram` / `sync-instagram-noticias`: `candidatos` cuenta POSTS recibidos; `emparejados`/`nuevos`/`descartados` cuentan FILAS de Neon (un solo post puede generar varias hijas). No comparable con las otras fuentes.
  - **Decisión: no normalizar** — no hay necesidad confirmada de comparar fuentes entre sí, solo de ver volumen y caídas por fuente a lo largo del tiempo, y para eso cada fuente contra sí misma basta tal como está. Si en el futuro hace falta comparar entre fuentes, normalizar entonces.
- **Cuatro fuentes** (una fila por ejecución de cada fichero):
  - `sync-events` (`api/sync-events.js`, al final del run): `candidatos` = eventos traídos de todas las fuentes antes del dedup; `emparejados` = ids que ya estaban en el `eventos-externos.json` anterior; `nuevos` = `agregados`; descartes = los de `combinarSinDuplicados()` (por url / por título+fecha). Ojo: corriendo en local sin `GITHUB_TOKEN` el JSON previo se lee vacío, así que `emparejados` sale 0 y `nuevos` lo es todo — artefacto del entorno, no un bug.
  - `deportes` (`api/_actividades-deportes-feed.js`, dentro de `obtenerActividadesDeportivas()` — también cuando el feed devuelve vacío): `candidatos` = carteles de la galería; `emparejados` = carteles que enriquecen un evento del programa de fiestas (subconjunto de `nuevos`, ver arriba); `nuevos` = actividades emitidas al cron. Identidad: `candidatos = nuevos + descartados`. Como la función la importan también scripts de diagnóstico (`scripts/contar-duplicados*.mjs`, etc.), esos scripts insertan filas si tienen `DATABASE_URL` (o loguean el fallo y siguen, si no).
  - `sync-instagram` y `sync-instagram-noticias` (al final de `procesar()`, también si el triaje falló a medias, y en el early-return de 0 posts): `candidatos` son POSTS recibidos pero `nuevos`/`emparejados` son FILAS creadas/actualizadas (un post puede crear varias hijas) — no tienen por qué cuadrar entre sí. Motivos: no normalizable, antigüedad/tope, rechazo del triaje del modelo, validación de la extracción, duplicado de evento existente (y en noticias: "ya existía como evento de agenda" y el gemelo de eventos de documento).
- **Fuera del log (deliberado)**: la regeneración de `noticias.json` dentro del cron (su cuenta va en `estadisticas.noticias` del resumen, es prensa, no eventos/actividades), los eventos creados a mano desde `/panel` (no son ingesta), y los scripts manuales `scripts/fetch-eventos.mjs` / `scripts/reprocesar-post-*.mjs`. Estos últimos no se instrumentan porque son **herramientas puntuales, no rutas de producción habituales**: `fetch-eventos.mjs` es la regeneración local del JSON y `reprocesar-post-*` es rescate manual de un post concreto. El dedup de un-evento-por-shortCode de `validarExtraccion()` que motivaba parte de esos rescates se arregló en ago-2026 (carruseles multi-evento, ver la sección del webhook): si `reprocesar-post-*` siguiera usándose con frecuencia, sería señal de que el arreglo no bastó — y de que el reproceso se ha vuelto ruta habitual y debe loguear como las demás. Tras ese fix, el motivo `"validación de la extracción"` de `sync-instagram` ya solo cuenta fallos reales de validación y repeticiones literales, no los demás carteles de un carrusel (verificado con el dataset real: el run pre-fix registró `descartados: 5` con ese motivo y el post-fix `nuevos: 5, descartados: 0`).

## Known issues and pending verification

### Deployment Protection bloquea también a los crawlers de vista previa

**Informativo, no bloqueante hoy.** El proyecto tiene `ssoProtection: all_except_custom_domains`: las **previews** están protegidas y el dominio público (`ennavalcarnero.es`) no. Comprobado en la preview de la rama del Open Graph dinámico: sin bypass, cualquier petición responde **302 a `vercel.com/sso-api`** — y eso le pasa igual a WhatsApp, Facebook o Twitter, que no saben autenticarse. Por eso **una preview nunca enseña vista previa enriquecida** al compartirla en un chat.

En producción no aplica, porque el dominio propio queda fuera de la protección. ⚠️ **Si algún día se activara la protección también sobre el dominio de producción, el Open Graph dejaría de funcionar en silencio**: nadie vería un error, simplemente las burbujas volverían a salir genéricas hasta que alguien comparta un enlace y lo note.

Para probar una preview hace falta el secreto de *Protection Bypass for Automation* (Project Settings → Deployment Protection; también se genera por API con `PATCH /v1/projects/<id>/protection-bypass` y `{"generate":{}}`). Se guarda en `.env.local` como `VERCEL_AUTOMATION_BYPASS_SECRET` (gitignored, nunca en el repo) y se manda como cabecera `x-vercel-protection-bypass`. Matiz que costó un ciclo de deploy: **la función se hace peticiones a sí misma** (`/api/eventos`, `/api/actividades`, `/api/eventos-ocultos`, `/index.html`) y esas también chocan con el SSO, así que `api/og-evento.js` **reenvía la cabecera de bypass entrante** a sus llamadas internas. Sin eso, en una preview el fail-soft las daba por caídas y componía los meta sobre la página de login de Vercel.

### Los `og:*` estáticos del `index.html` apuntan al dominio equivocado

**Sin arreglar — deuda anterior al Open Graph dinámico, deliberadamente fuera de su alcance.** `index.html` declara `og:url` y `og:image` contra `https://naval-app-one.vercel.app/…` cuando el dominio real es `ennavalcarnero.es`. ### El extractor de eventos clasifica como "evento" pruebas participativas con plazo de inscripción

**Sin arreglar todavía — solo documentado.** El prompt de extracción de `api/sync-instagram.js` acepta como evento cualquier cartel con fecha+hora+lugar de un acto, aunque el cartel lleve además un **plazo de inscripción explícito** ("Inscripciones: hasta el 25 de agosto…"). Cuando el acto es una **prueba/torneo/competición participativa con plazo**, el criterio del proyecto —ya escrito para el webhook de noticias, decisión ago-2026: "torneos/carreras/marchas aunque la inscripción sea el mismo día SON actividades con `fechaLimite` = día de la prueba"— dice que es **actividad**, no evento de agenda. Verificado con el post `DcIj1xrj0tG`: 3 de los 9 carteles deportivos con plazo (Torneo de tenis 26 ago–5 sept, Torneo de pádel, Juegos deportivos para niños) salieron como evento; como el webhook de noticias no había creado actividad gemela para esos tres, el cruce manual eventos↔actividades tampoco los cazó, y se archivaron a mano el 2026-08-24 (las 6 hijas del carrusel acabaron archivadas: 1 pasada, 2 duplicadas con actividades y estas 3 mal clasificadas; el Duatlón `ig-DcIj1xrj0tG` sigue publicado). No se crearon las actividades equivalentes a mano — la vía correcta es corregir el extractor.

⚠️ Al arreglarlo, el criterio es **estrecho**: prueba/torneo participativo CON plazo ⇒ actividad. NO vale descartar "cualquier mención de inscripción" — un concierto con aforo limitado o reserva de entrada sigue siendo un evento de agenda. El caso del tenis enseña otra señal útil: un cartel "del 26 de agosto al 5 de septiembre" (rango multi-día de competición) tampoco es el evento puntual que el modelo fabricó con la fecha de inicio.
